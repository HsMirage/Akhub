# 计划与实现偏差审计（2026-09-15）

对照 `计划.md` 逐节核对当前 `master`（v1.0.0 之后）。结论：核心链路（协议、调度、
限额、安全、部署、SDK 验收）已达标；**后台信息完整性与可观测性**是主要欠账，
集中在概览、请求记录、成本三处。以下按优先级列出。

## P1：计划明确承诺、当前缺失

### 1. 请求记录缺 Token、首字延迟与每次尝试明细（§6.6）

计划要求记录"每次尝试的目标、端点、耗时和失败原因，以及该次失败是否计入尝试
预算""首字延迟、总延迟、Token、切换次数和配置版本"。

现状：`request_records` 每请求一行，只有 `attempts` 计数与最后一次目标，
没有逐次尝试明细；没有 token 列、没有首字延迟列、没有配置版本列。
`tests/` 里的 `RequestRecord` 结构也只覆盖现有列。

影响：请求记录无法回答"这一次为什么换了三个号、每个号耗时多少、消耗多少 token"。

建议：新增 `request_attempts` 表（request_id, seq, target_id, endpoint, duration_ms,
outcome, counts_against_budget）与 `first_token_ms` / `input_tokens` / `output_tokens` /
`config_version` 列；结算路径一次写入。

### 2. 请求记录页没有筛选（§6.6）

计划要求按时间、请求 ID、分组、逻辑模型、实际目标、状态、错误码筛选。

现状：`GET /admin/api/requests` 只接受 `limit/offset`，前端也只有分页。

建议：给接口加过滤参数与索引，前端加筛选栏（分组/模型/状态/错误码/请求 ID/时间范围）。

### 3. 成本页没有 token 用量（§6.8、§11.6）

计划要求"以逻辑模型为单位"显示 token 用量与占比，并明确不跨模型加总。

现状：`request_records` 不存 token，成本页只能显示请求数与倍率，无法显示
"本月 100 万 token"与 token 占比——这是与计划最直观的偏差。

依赖：与 P1-1 同一份数据（先补 token 列，再聚合）。

### 4. 概览页缺运行指标与告警（§6.2）

计划要求：请求量、成功率、平均/高位延迟、在途请求数、排队请求数、队列超时数、
最近错误、最近配置变化、倍率探针系统性故障告警。

现状：已有目标状态分类、倍率过期/未知、系统性故障标志、粘性绑定数、端点缺失、
丢弃记录数；缺请求量/延迟聚合（可从 `request_records` 算）、在途与排队计数
（需要运行时计数器）、队列超时数、最近错误与配置变化（审计表已有数据未上屏）。

### 5. 账号列表没有筛选（§6.4）

计划要求按分组、状态、上游类型筛选。现状：前端无筛选器（接口返回全量）。

## P2：偏差或未定义清楚，需要确认

### 6. 分组"最长等待时间"（§6.3）

计划的分组页要求显示"队列总容量和最长等待时间"。当前数据模型只有
`queue_capacity`，等待时间由请求总超时（`request_timeout`）统一约束。
需要确认：是补一个分组级最大等待字段，还是把"最长等待"理解为请求总超时并在页面标注。

### 7. 图片接口与计划冲突（计划 §2.2 / §29）

计划写明"不做图片生成…独立 API 端点"，后续按你的要求已实现
`/v1/images/generations` 与 `/v1/images/edits`（仅原生转发）。建议更新计划文本，
否则审计会一直把它标成偏差。

### 8. 后台响应（§15.3）的粘性未做端到端验收

查询/取消已按"有原生映射就代理、没有就明确拒绝"实现；但"`background:true`
创建后固定目标、倍率变化不迁移"这条完整生命周期还没有针对真实上游的验收用例。

## P3：已实现但与计划的措辞不一致（低风险）

- §6.6 "配置版本"：配置快照版本号已在概览返回，但没有写进请求记录。
- §6.4 "复制后打开编辑页"：当前复制完成后停留在列表（体验差异）。
- §6.2 "最近配置变化"：`admin_audit_log` 已在写入，但概览未展示。
