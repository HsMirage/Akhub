## 修复：跨渠道的思考块签名 400 直接透传给客户端

### 现象

Claude Code 类客户端在 `claude-opus-5-5` 上偶发收到：

```
400 messages.8.content.0: Invalid `signature` in `thinking` block
```

而同一段会话换一次就正常。

### 现场（24 小时，生产库 + 容器日志）

- 该文案的日志 **9 条**，`account` 全部是 **可达鸭-ccmax**（kedaya.ai 的 Claude Code Max
  渠道），其余账号 0 条。
- 全部属于**同一个会话**：分组 `grp_01M3TX…`、`claude-opus-5-5`、passthrough、
  `effort=max`，请求体从 338 KB 一路长到 983 KB。
- 02:00 之后该分组 opus-5-5 共 331 次请求：`可达鸭-ccmax` 被抽中 **7 次、7 次全 400**；
  其余 5 条渠道 **324 次全 200**。
- 最干净的对照：`10:15:41` 可达鸭 400（983,107 B）→ `10:15:43`
  `supeai.cc-ccmax-0.85` 200（956,032 B）。
- 用户报的那条能对上：错误里的上游 request id `20261026100832…` = 10:08:32 UTC =
  库里的 `req_01M5VTXRREN7MN853RN3X70Z76`（910,248 B；第 1 跳 wishtoapp 回
  “会话不可路由”，第 2 跳可达鸭回这条 400）。

### 根因

1. 客户端不发会话 ID / `prompt_cache_key`，粘性键落到“稳定前缀”
   （`src/routing/sticky.rs`）→ **弱绑定**：不钉目标，只做 Key 亲和，每轮目标重新抽
   （`src/gateway/passthrough.rs`）。这条会话因此在 supeai 正价 / supeai ccmax /
   可达鸭-kiro / 可达鸭-ccmax 之间来回跳。
2. `可达鸭-ccmax` 倍率 **0.8**，同层最便宜，于是偶尔被抽中。
3. 它的 thinking 签名**只认自家签发的**：会话在别家渠道跑过之后再回来就 400
   （01:45 之前同一会话在它上面还是 200，中间几轮被别家签过名）。
4. 决定成败的一步：这句 400 含 `invalid`，被 `is_opaque_rejection` 的“可归因”
   清单判成客户端参数错误，于是**不换渠道、直接透传**。而它发生在上游开始生成
   之前、没消耗一个 token，与 §13.7 的“无法归因 400”一样，换渠道几乎免费。

### 修复

新增 `is_foreign_thinking_signature()`：400 且同时含 `signature` + `thinking` +
`invalid|not valid|mismatch|does not match` 时，按 `OpaqueRejection` 处置——不计
目标故障、换渠道重试（最多 2 个额外目标），全部失败才把上游原话返回。判据特意
排除 `thinking.signature: Field required`、`thinking.type: unknown variant` 这类
真·形状错误（换渠道不会变好）。
