## 一、结论

**这三条 400 不是被上游的旧格式打中的，是被 Akhub 自己的「档位事实库」打中的。**

上游那条渠道确实有问题（那是上游的事，我们改不了）。但 Akhub 本该做的事是：第一次 400 就把请求交给另一个账号 —— 它没做，而是在**同一个目标上把档位来回改**，最后把上游的 400 原样透传给用户。

四个环环相扣的缺陷：

1. **事实库自相矛盾**：`EffortFacts` 用两张互不清除的位图记「接受过」和「拒过」。`plan()` 的第二分支只看 `is_accepted`，不看 `is_rejected` —— 一个**已经被拒过**的档位，只要历史上成功过一次，就仍然是「已确认可用」的首选。现场日志逐字留下了这个往返：`high → xhigh → max → xhigh`。
2. **形状守卫只比相邻两次**：`if adaptive_shape(&next.body) == adaptive_shape(&prepared.body)` 拦不住 `A → B → A` 这种往复。
3. **收敛后的失败是静默的**：形状没变就 `Terminal` —— 不打日志、不记 `upstream_status`、不记 `error_code`。库里那三条 400 事后完全无法归因（`attempts=1`、两个状态码都是 NULL），日志里一个字都没有。
4. **档位阶梯走完不换渠道**：三处 `Terminal` 直接结束请求，而同分组还有 3 个账号可用（同一模型名在另外两个 target 上有大量 200）。

代价不只是那三条 400：**该账号上每个带 `effort` 的请求平均要多打 2–3 次上游**（151 条「改按可用档位重发」日志 / 59 个 request_id），延迟白增 3–13 秒，上游配额白烧。

| # | 事件 | 事实库 | `plan(high)` | 发给上游 |

## 三、根因（代码级）

### 3.1 「接受过」与「被拒过」互不排斥 —— 乒乓的直接原因

```rust
// src/upstream/evidence.rs:131-137
fn accept(&mut self, level: Effort) { self.accepted |= level_bit(level); }
fn reject(&mut self, level: Effort) { self.rejected |= level_bit(level); }

// src/upstream/evidence.rs:172  —— plan() 的第二分支
if let Some(higher) = self.lowest_above(requested, |facts, level| facts.is_accepted(level))
```

`is_accepted` 只看 `accepted` 位图（evidence.rs:143-145）。同一档位先进 `accepted`、后进 `rejected`，它**同时**是「已确认可用」和「已被拒」。而 `plan()` 的优先级（evidence.rs:163-164 注释）是「升到已确认可用的更高档 > 往上试探一档 > 不指定」—— 于是矛盾态下永远选前者，**反复重发同一个已被拒的档位**。

单测没有覆盖这个组合：evidence.rs:298-421 六个用例里没有任何一个同时 accept 与 reject 同一档位。

### 3.2 守卫只比相邻两次形状

```rust
// src/gateway/passthrough.rs:1669-1671
if adaptive_shape(&next.body) == adaptive_shape(&prepared.body) {
    return Err(AttemptFailure::Terminal(response));
}
```

`A → B → A` 每一跳都与上一次不同，守卫放行，直到 `MAX_EFFORT_RETRIES = 6`（passthrough.rs:72）或形状偶然不变才停。

### 3.3 静默 `Terminal`（三处 + 两处）

| 位置 | 触发 |
|---|---|
| passthrough.rs:1655 | `effort_retries == 0` 或超过 deadline |
| passthrough.rs:1666 | `prepare_with_reject` 失败 |
| passthrough.rs:1670 | 形状没变 |
| passthrough.rs:1828 | multipart 模型名重写失败 |
| passthrough.rs:1868 | `translation.emit` 失败 |

五处都不打日志。结果分支（passthrough.rs:1437-1448）也不记 `error_code` / `upstream_status`：

```rust
admission.settle(health::Outcome::Neutral, None);
let status = response.status();
self.note_attempt(candidate, started, "failed", None, true);
self.finish(Some(candidate), status, None, None, *response)   // ← upstream_status 恒为 None
```

只有成功路径（passthrough.rs:1387-1414）传 `Some(success.status)`。这解释了全库的形态：

```sql
select http_status, upstream_status is null, count(*) from request_records group by 1,2;
-- (200,0,151573)  (400,1,821)  (429,1,1104)  (503,1,8077) …
```

**所有失败请求的上游状态码都是 NULL**，库里也不存上游错误正文。

### 3.4 换渠道机制在真实流量里形同虚设

`MAX_OPAQUE_REJECTION_RETRIES = 2`（passthrough.rs:80）的换渠道重试只对「无法归因的 400」生效 —— 文案必须命中 `could not be processed` 之类（passthrough.rs:3419-3425）。而现场这句 `requires adaptive thinking; …` 含子串 `thinking`，命中 ATTRIBUTABLE 名单（passthrough.rs:3385-3413），一律判为可归因。

量化结果（生产实测）：该分组该模型全时段 400 = 120 条 —— `attempts=0` 10 条（网关自己生成，没打上游）、`attempts=1` **105 条**、`attempts=2` 仅 5 条、`attempts=3` 零条。**120 条里 115 条（96%）一次都没有换过渠道。**

## 四、可以优化体验的地方（按性价比排序）

### P0-1 事实库：让「被拒」压过旧的「接受过」—— 已实现

- **问题**：矛盾态让 `plan()` 反复选中已被拒的档位（3.1）。
- **改法**（最小且语义清楚）：在 `accept`/`reject` 里互清对应位 —— 最近一次观测说了算。已落地在 `src/upstream/evidence.rs:136-145`：

  ```rust
  fn accept(&mut self, level: Effort) {
      self.accepted |= level_bit(level);
      self.rejected &= !level_bit(level);   // 新增
  }
  fn reject(&mut self, level: Effort) {
      self.rejected |= level_bit(level);
      self.accepted &= !level_bit(level);   // 新增
  }
  ```

- **不动的口径**：`plan()` 的「只升不降」（计划.md §14.6）保持不变 —— 被拒档位仍然往上找，只是不再把「历史成功」当免死金牌。
- **回归测试**：`a_level_accepted_then_rejected_is_no_longer_treated_as_known_good`（`src/upstream/evidence.rs`，先 reject High → accept XHigh → reject XHigh，断言 `plan(High) == Send(Max)`，即不再把 XHigh 当「已确认可用」；反向顺序断言 `Send(XHigh)`）。
  - 第一版写错过一次：只 reject/accept 同一档 XHigh 就断言 `plan(High)==Send(Max)`，实测是 `Send(High)` —— 因为 High 本身没被拒，`plan()` 第一分支就返回了。要断言「升级路径」，必须先把客户端原始档位标成 rejected。
- **代价**：一个档位在 24h TTL 内被接受过又被拒，之后不再算「确认可用」，退回「往上试探」或 `Omit`。这正是我们想要的。

### P0-2 守卫：记住本轮发过的形状，重复即停 —— 已实现

- **问题**：`A → B → A` 拦不住（3.2）。
- **改法**：把本轮已发过的 `AdaptiveShape` 收进 `sent_shapes`，命中重复就停（仍然保留 `MAX_EFFORT_RETRIES` 上限）。已落地在 `src/gateway/passthrough.rs:1731`（初始化）与 `:1787-1790`（重复即 `EffortExhausted`）。
- **效果**：现场第 1 条请求会在第 3 次上游调用前停下，省掉一次白撞。
- **回归测试**：`a_shape_this_round_already_sent_is_not_sent_again`（`tests/protocol_e2e.rs`）。用新增的 `Behavior::HangThenJson` 把第 3 跳挂住，`wait_for_requests(3)` 后**在网关重试途中**给同一账号写上 `xhigh accepted`（复刻现场 16:32:07 那条并发 200），再放行：断言 `levels == [high, xhigh, max]`、`upstream.requests() == 3` —— 第 4 跳不会回到已经发过的形状。

### P0-3 阶梯走完要换渠道，而不是直接失败 —— 已实现

- **问题**：三处 `Terminal` 立即结束请求，即使同分组还有别的账号/target 可用。现场 AwsClaude 有 4 个账号，同一模型名在 `tgt_01M4520KJSZH5T8MWZDX8YSC4M`、`tgt_01M4QHJG4YYGEVWFCEHTKXQ8X7` 上有大量 200。
- **改法**：新增 `AttemptFailure::EffortExhausted { status, message, public }`（`src/gateway/passthrough.rs:275-279`），三处 `Terminal` 改成返回它；结果分支（`:1545-1601`）按「无法归因的 400」同款处置 —— `admission.settle(Neutral)`、`note_attempt(..., "effort_exhausted", None, true)`、独立计数器 `effort_exhausted_retries`（与 `opaque_rejection_retries` 分开，`MAX_OPAQUE_REJECTION_RETRIES = 2`）、`Flow::Continue` 换下一个候选。
  - 另外补了一条归因：形状**本来就是** adaptive、档位已经降到「不指定」，上游还回同一句 `requires adaptive thinking` 时，这句话与请求无关，直接判 `EffortExhausted`（`src/gateway/passthrough.rs:3490-3511`）——否则它会掉进 `is_opaque_rejection` 的 ATTRIBUTABLE 名单，被当成可归因 400 直接透传。
- **理由**：400 发生在生成之前、零 token 消耗，换渠道几乎免费 —— 与 docs/2026-10-13_部署-Akhub-v1.1.30-report.md 里对不透明 400 的处置口径完全一致（代价不对称）。健康结算仍用 `Neutral`，不把账算到目标头上（计划.md §12.3）。
- **回归测试**：`an_exhausted_effort_ladder_switches_target`（`tests/protocol_e2e.rs`）。两个 target 同 base_url、priority 60/50，用 `Behavior::PerKey` 只让 `key-refuse` 拒：断言最终 200、`requests_with_key("key-refuse") == 4`（阶梯在自己身上走完）、`requests_with_key("key-healthy") == 1`。
- **预期**：现场这 4 条里至少 3 条会换到别的 target，大概率直接 200。

### P1-1 失败请求记下上游状态码 —— 已实现

- **问题**：`upstream_status` 恒为 NULL（3.3），事后无法判断「上游拒绝」还是「网关自己生成」。
- **改法**：`AttemptFailure::Terminal` 携带 `Option<StatusCode>`（`src/gateway/passthrough.rs:227`），在结果分支（`:1486-1500`）传给 `finish`；候选耗尽兜底（`:807-813` 一带）也把 `opaque_response()` 的状态码记进去。网关自己判定的参数错误传 `None`。
- **效果**：下次 400 在请求记录里就能看到「上游 400」。
