## 为什么重部署一次

第一次的二进制是在编译机上用**旧的** `web/dist` 编译的：本地 dist 是 11-14 构建的，
而 `web/src` 在 11-19 还有一次改动（`6d1087e`，请求记录「粘性未保持」那处）。
结果 1.1.55 内嵌了旧前端 `index-ltBm-zCB.js`，1.1.54 镜像是 `index-podm9R_6.js`。

发现方式：对比旧二进制（备份里的 1.1.54）与新二进制里的内嵌资源名。
处置：本地 `cd web && npm run build`（产物正好是 `index-podm9R_6.js`）→ 同步
`web/dist` → 编译机重编译（`cargo build --release` 后再跑
`cargo test --release --test admin_api` 23 通过）→ 重新部署。

教训：同步源码到编译机时 **`web/dist` 不能跟着 `.gitignore` 一起被排除**；
或者部署前必须核对内嵌资源名与上一版一致/更新（`strings <二进制> | grep index-`）。

## 待观察（本次改动的重点）

上游「迟迟不给响应头」时，应在 `first_content_grace`（15 秒）后先收到响应头与
`: keep-alive` 注释帧，真内容随后接上；原先 120 秒零字节的 524 应该消失。

部署时上游很快（首字 2–3 秒），自然样本里最慢的首字 15.0–20.5 秒都正常 200，
暂时没抓到「>120 秒沉默」的现场样本。观察口径：

- nginx `/v1/messages` 的 499 里 `rt>110` 的条数应为 0（改动前一小时有 10 条）；
- 客户端侧首字不再卡在 120 秒整；早提交之后的失败会变成更早出现的
  `200 + event: error`（流内错误帧），而不是 524。
