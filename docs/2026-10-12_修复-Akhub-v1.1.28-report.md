# Akhub v1.1.28：Key 池的粘性、诊断与 429 归因

## 结论

1.1.28 修了 Key 池（§4.2.1）上三个会**实际劣化线上缓存命中率**的缺陷，并把
"这次请求走的哪把 Key"第一次落进数据库。

起因是 2026-10-11 的一次排查：hyper.charm.land 的 `deepseek-v4.1-flash` 缓存命中率只有
15%，而同账号、同 Key 池的 `glm-5.3-flash` 是 91%。根因不在上游，在网关自己。

## 三个缺陷

### 1. 粘性绑定被静默抛弃（主因）

`credential::select_key` 把"钉住/粘性"当作**可用 Key 之间的偏好**：绑定的那把只要
这一刻"忙"（并发或限额满），就静默回落到池里均匀抽签。

上游的前缀缓存**按凭据隔离**——实测同一前缀换一把 Key 立刻 `cached=None`，换回来又命中；
命中与未命中的成本差约 9.7 倍。于是"这把 Key 恰好满"就等于"这段缓存作废"。

生产证据（近 6 天，同一账号、同一目标、同一前缀的相邻重复请求）：

| 判定 | 次数 |
|---|---|
| 跨账号漂移 | **0** |
| 同账号同目标、缓存命中 | 9,723 |
| 同账号同目标、缓存**未命中** | 722 |

跨账号漂移为 0，说明账号层粘性是好的；未命中全部发生在**账号和目标都没变**的情况下——
只可能是 Key 换了。全库对照命中率 93.1%，而 hyper 的 21 Key 池只有 67.8%。

**修复**：`KeyChoice` 增加 `BoundBusy`——绑定的那把只是"忙"时，调用方**为它等待**
（等待对象是那一把，不是"任意一把"）；只有它**不再合格**（停用、熔断、额度耗尽、被删）
才换 Key。设计文档 §2.2 早就写死了这条规则，代码没实现。

### 2. `run()` 重复选 Key，破坏不变量 A（修复过程中发现）

调用方 `try_candidates` / `wait_and_run` 的流程是"选 Key → 用**那一把**的额度做准入
→ 发起尝试"，但 `run()` 内部**又选了一次**。后果有两个：

* 可能选出另一把 Key：**并发名额记在 A 上、请求发给 B**——不变量 A（一次下游调用只
  用一把 Key）被破坏；
* 刚占下名额的那把 Key 在自己的准入检查里显示"已满"，**把自己挡在门外**，请求直接
  503 `no_eligible_target`。

第 2 点就是缺陷 1 的修复在单 Key 上也暴露出来的原因：原先"忙→换一把"的回落恰好掩盖了
这个自我阻塞。**修复**：`run()` 改为接收调用方已选定并已准入的那把 Key，不再重选。

### 3. 429 只记目标，不记 Key

`Admission::settle` 的 `RateLimited` 分支只把限流记在"账号 + 模型"的目标熔断上。
但上游限流可能**按凭据计**，而池里每把 Key 是独立额度。漏记 Key 级有两个后果：一把
Key 被限流会连累同账号其他 Key；这把 Key 在下一轮抽签里还会被选中、继续撞 429。

**修复**：多 Key 账号里，429 同时记在目标与该把 Key 上；单 Key 账号只记目标一次
（Key 与账号是同一个调度单位，记两遍只会让两级冷却互相错位）。

## 诊断能力：key_id / key_label 落库

`request_records` / `request_attempts` / `response_states` 三张表的 `key_id` 列
**一直存在但从未写入**（生产 0/133,466）。`RequestRecord` 结构体根本没有这两个字段，
两条 INSERT 也没带这两列。

这次全部补齐并端到端验证：

* 主记录与尝试明细都记下行 ID 与标签（换 Key 重试时同一条请求会留下多条不同 Key 的明细，
  "换了几把才通"一目了然）；
* `response_states.key_id` 同步落库——上游的 `resp_xxx` 是凭据隔离的资源，续写与
  生命周期代理必须回到同一把 Key，否则上游只会回 404。

**凭据本身绝不落库**，只存行 ID 与管理员自己填的标签（§23.4、§24.1）。

## 顺带修复

* `capacity` 路径把 Key 的**行 ID** 当 `key_id` 传给了 `health::Caller`，而
  `Registry::keyed` 期望的是**凭据摘要**。这会另开一份永远匹配不上的"影子状态"——
  排队等的是影子，真正那把 Key 的名额照样被占着。

## 数据结构

**无 schema 变更**：`key_id` / `key_label` 三列在 v10 迁移里就已经建好，只是从未写入。
新旧二进制可以直接互切。

## 限制

* 单 Key 账号的行为**完全不变**（唯一那把 Key 就是账号），429 仍只记目标一次。
* 429 的归因仍然有歧义：上游通常不告诉你它是按模型还是按凭据限流，所以两级都记——
  这是有意的取舍，代价是多一级冷却。
* 本版**未**改动 `select_key` 的抽签权重：Key 之间仍是均匀随机。设计文档 §12 明确
  "不做 Key 级性能 EWMA 分表"，本次遵循该口径。
