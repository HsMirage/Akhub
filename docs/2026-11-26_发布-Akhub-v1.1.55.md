# 发布 Akhub v1.1.55：上游迟迟不给响应头时，源站也先开口（消灭 524）

## 现场

2026-11-26 11:39（+08），sub2api 的「Claude Ultra」分组调 claude-opus-5-5，
客户端收到 Cloudflare **524**（ray `a605da047992dcb1`）：

| 层 | 证据 |
|---|---|
| nginx（源站） | `POST /v1/messages?beta=true 499 0 rt=125.007 urt=125.006 ust=-`：上游一个字节都没给 |
| sub2api | `gateway.forward_failed.client_gone`，`latency_ms=125066`，`Post http://89.58.17.138:8088/v1/messages: context canceled` |
| Akhub | Claude Ultra 分组里 claude-opus-5-5 只启用了三个可达鸭渠道；同窗口可达鸭-cursor 的尝试 30.5/46.1/60.8/106.8 秒超时，另一次 **122.7 秒**才拿到首字 |

根因不是 Cloudflare 也不是 nginx：**上游在交出响应头之前沉默了 120 秒以上**。
v1.1.52 之前加过"首字前心跳"，但它只覆盖"上游响应头已到、还在等首个语义事件"
那一段；**连响应头都还没到**的那一段仍然是零字节，而 CDN 判 524 判的正是这一段
（[2026-10-14 根因报告](2026-10-14_opus-5-5-522-524-根因报告.md) 留下的尾巴）。

## 改法（`src/gateway/passthrough.rs`）

- 新增"早提交"：流式推理请求（`/v1/messages`、`/v1/chat/completions`、
  `/v1/responses`）在 `first_content_grace`（默认 15 秒，另夹一层 90 秒硬上限）
  内拿不到上游响应时，**先把 200 + `text/event-stream` 交出去**，由
  `stream::keep_alive_until_ready` 每 `keep_alive_interval`（默认 5 秒）发一帧
  `: keep-alive` 注释帧保活；真正的上游响应就绪后原样接上它的响应体。
- 失败收尾：响应头已经发出就改不了状态码，网关错误体的 JSON 按下游协议包成流内
  错误帧（Anthropic/Responses 用 `event: error`，Chat 用 `data:`）；读不出 JSON
  时按状态码归类的通用错误帧兜底。
- 多目标切换不受影响：切换本来就在"拿到首个语义事件之前"进行，早提交只是把
  响应头先放行，转发仍然在响应体里继续跑。非流式请求不启用（没有合法的保活形式）。
- 为了把"请求输入"带进响应体，`Forward` 从借用改成自持（`Arc` / `String` /
  `HeaderMap`），否则下游 body 的 `'static` 约束满足不了。

## 取舍（必须知道）

- 预算耗尽之后这次请求的 **HTTP 状态码就固定为 200**：之后上游报错会以流内错误帧
  到达，客户端看到的不是 429/504，而是 200 + `event: error`。想保留更长的"状态码
  可切换"窗口就把 `first_content_grace` 调大（上限 300 秒，但必须远离 CDN 的
  120 秒——早提交这里另有 90 秒硬上限兜底）。
- 早期路径不再携带 `x-akhub-degraded` 这类响应头（响应头提前发出，后到的头没有
  位置可放）。降级信息仍在请求记录里。

## 已知局限

- 非流式请求仍然可能被 CDN 判超时：它没有合法的保活形式，只能靠上游尽快给
  `response_timeout` 内的响应。当前线上 Claude 流量全部是流式。
- 早提交之后的失败会以 200 + 流内错误帧到达；依赖 HTTP 状态码做重试决策的客户端
  会少一次重试机会（sub2api 会按流内 `error` 帧处理）。
