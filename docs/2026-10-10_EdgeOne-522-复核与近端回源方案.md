# ai.hsnb.fun 偶发 522 复核与近端回源方案

- 复核时间：2026-10-10 18:20 → 22:20（北京）
- 源站：`89.58.17.138`（德国，New API 面板机；宿主 hostname `Vienna`）
- 用户侧报错（原文）：

  ```json
  {"error":{"type":"bad_response_status_code","message":"bad response status code 522 (request id: 202610100836477052970008268d9d603tehVJh)"},"type":"error"}
  ```

- 前序报告：[2026-10-09_新建令牌522-根因报告.md](2026-10-09_新建令牌522-根因报告.md)（已给出"EdgeOne 边缘回源超时"的方向，本报告把错误链路的归属和处置方案补完）

## 一、结论

1. **522 依然是腾讯 EdgeOne 边缘节点返回的**。触发条件是「边缘 → 德国源站 `89.58.17.138:443` 的**回源 TCP 建连**超过 EdgeOne 的源站连接超时（约 5s）」。劣化时段里坏边缘 POST 稳定在 **5.13–5.26s** 返回 522；同刻健康边缘 0.9–1.2s 返回 401。**源站、Akhub、本机 new-api 全程没有产生过任何 522。**
2. **用户贴的这段 JSON 不是我们的栈产生的**，而是**下游另一个 new-api 实例（客户自己的面板/中转站，把 `ai.hsnb.fun` 当上游渠道）**把 EdgeOne 的 522 二次包装出来的；其中的 `request id` 是**那个实例自己的请求号**，与定位本次故障无关。

> 换句话说：客户侧看到的是"他们的网关把我们的 CDN 错误包了一层"，而根因在 **CDN 边缘 → 德国源站的建连**这一段。

## 二、错误串溯源（为什么能确定不是本机产生）

1. `bad response status code %d` 是 **new-api 的固定文案**（`service/error.go:87 RelayErrorHandler()`）：上游返回非 2xx 且响应体不是 JSON（EdgeOne 的 522 是 `content-length: 0`）时，走 `service/error.go:111` 生成**不带 body** 的 `bad response status code 522`——与用户看到的文案逐字一致；` (request id: …)` 由 `middleware/utils.go:26` + `common/utils.go:268 MessageWithRequestId()` 追加。
2. **请求号的结构**（`common/utils.go:243-258`）：
   - `GetTimeString()` = UTC `20060102150405` + 9 位纳秒 = 23 字符；
   - `requestIdPrefix = hex(sha256(bi.Main.Path))[:8]`，`bi.Main.Path` 是编译进二进制的 Go 主模块路径；
   - 本机 new-api 的模块路径为 `github.com/QuantumNous/new-api`，`sha256("github.com/QuantumNous/new-api")` 前 4 字节 = `8268d9d6`。
   - 所以 `20261010083647 705297000 8268d9d6 03tehVJh` 解出来是：**UTC 2026-10-10 08:36:47.705297** + 构建前缀 `8268d9d6` + 8 位随机。**构建前缀是"同一套码编译出来的所有 new-api 实例都一样"的常量**，不能用它判断是哪台机器（这点在 10-10 当天一度被误读，特此记录）。
3. **本机没有产生这条错误的反证**（均已实测）：
   - 该 request id 在 new-api `logs` 表中按 `request_id` 与 `upstream_request_id` 均查不到；
   - 本机 new-api 全库 `content like '%bad response status code%'` = **0 行**；
   - 全量 nginx 日志（`access.log` + 全部归档）里 `" 522 ` = **0 行**；
   - Akhub `request_records` / `request_attempts` 中 `upstream_status=522` 或 `http_status=522` = **0 行**（Akhub 自己的请求号形如 `req_01M4JQ…`，与 new-api 的 39 字符格式无关）；
   - 该时刻（16:36:47 北京）源站 nginx 没有任何 `/v1` 请求。
4. **完整链路**：

   ```
   客户侧 new-api 面板 ──▶ ai.hsnb.fun（EdgeOne 边缘）──回源建连超时──▶ ✗ 522（空 body）
        ▲                                                                        │
        └──────────── 面板 RelayErrorHandler 包成 "bad response status code 522 (request id: 自己的)" ◀─┘
   ```

**结论**：源站健康，问题在"大陆边缘 → 德国"这段国际链路的**建连阶段**（TCP 握手在 5s 内完不成），不是源站拒绝连接。

## 五、解决方案

### 方案 A（推荐 · 治本）：香港近端回源中转

EdgeOne 源站从德国改成**香港中转机**（腾讯云 `47.76.54.171`；东京 `43.128.225.152` / `8.211.163.172` 可做备用源站）。大陆边缘只连香港（RTT 数十毫秒、走腾讯骨干），中转机再走数据中心线路到德国源站。

- 已交付：[`deploy/edgeone-relay/`](../deploy/edgeone-relay/)（`setup-relay.sh` 一键部署 + SNI 白名单 L4 透传 + sysctl/BBR 调优 + 自测；`rollback-relay.sh` 回滚；README 含控制台切换步骤）。
- 若中转机 443 被占用：`RELAY_PORT=2443`，并在 EdgeOne 同步改"回源端口"。
- 切换后源站 `$remote_addr` 变成中转机 IP：在源站 nginx 取消注释已预置的 `set_real_ip_from / real_ip_header / real_ip_recursive`（模板见 `newapi.conf` 末尾）即可还原真实客户端 IP。
- 代价：境内多一跳（数十毫秒）；中转机承担全部回源流量（注意轻量套餐带宽/月流量）；中转机本身要监控。

### 方案 C（临时兜底）

- 受影响省份用户改走 `ai-cf.hsnb.fun`（Cloudflare 路径；大陆实测 POST 基本能通，但耗时波动大：0.9–13.4s，偶发数十秒无响应）；
- 客户端对新 API 面板的写操作（新建令牌等）加重试 1–2 次：522 是**连接层失败**，重试通常落到好边缘；
- 面板侧可对 522 做一次自动重试（new-api 渠道配置里的重试次数）。

### 方案 D（已完成）：源站加固

见第七节。与 522 无直接因果，但降低源站侧风险面、并为后续排查留证据。

## 八、遗留待办
