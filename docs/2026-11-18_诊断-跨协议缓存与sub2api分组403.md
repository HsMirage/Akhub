## 一、Akhub：Claude Messages → OpenAI 兼容之后缓存掉了

### 结论

上游的**缓存路由提示根本没送到上游**，不是上游不缓存。两个缺陷叠加：

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | 粘性键不认 Anthropic 的 `metadata.user_id` | `src/routing/sticky.rs` 第 3 级 | 整条 Messages 流量掉到第 4 级「稳定前缀」 |
| 2 | 跨协议发射时把会话标识整个丢掉 | `src/protocol/anthropic.rs` → Chat/Responses | 上游既不知道同一会话，也没有分片提示 |

### 证据 1：现场 99% 的 Messages 请求用的是「稳定前缀」那一级

```
protocol=anthropic_messages，近 3 天，HTTP 200：
group                            n      cache_key  stable_prefix
cursor反代                       3431        0         3423
AwsClaude                        2319        0          710
ccmax                             928        0          922
正价-claude                       311        0          311
```

`sticky_origin=cache_key` **一条都没有**。而同期 Chat / Responses 有正常的
`cache_key` 与 `session_header` 命中，说明不是采集问题，是这一级对 Messages 不成立。

Claude Code 每轮都在 `metadata.user_id` 里带
`user_<64hex>_account_<uuid>_session_<uuid>`（sub2api 也按这个格式解析，
见 `metadata_userid.go`）。Akhub 的第 3 级只读了 `prompt_cache_key` 和 `user`，
两者 Anthropic 请求体里都没有，于是落到第 4 级。

第 4 级的语义是「同一个 agent 项目」：**同一个项目里并行的多条会话共用同一个前缀、
同一个绑定**，互相把对方顶出去，每次抽签都可能换账号。上游的前缀缓存按凭据隔离
（§2.2 不变量 B），换一次号就是整份缓存重建——表现正是「好像没有缓存」。

### 证据 2：发往 OpenAI 上游的请求体里没有缓存提示

`parse_request` 把 `metadata.user_id` 只塞进 `request.user`。转成 Chat 时发成
`user` 字段，转成 Responses 时同样；**`prompt_cache_key` 永远是 `None`**。
OpenAI 侧的缓存亲和完全依赖 `prompt_cache_key`（`cache_control` 是 Anthropic 专有，
OpenAI 上游不认）。所以即便网关这一侧把会话钉在一个账号上，上游仍然把每一轮当成
新会话，缓存分片跟着漂。

顺带说明 Responses 那侧：`openai_responses.rs` 的 `KNOWN_FIELDS` 里
`prompt_cache_key` 是认的、发射也是照发的，只是**源头没有值**。

### 修改（已做，两个文件）

1. `src/routing/sticky.rs`：第 3 级增加 `metadata.user_id`，与 `prompt_cache_key`、
   `user` 并列。命中它就走**强身份**（钉死绑定），不再走弱身份的软亲和。
2. `src/protocol/anthropic.rs`：解析时同时写入 `request.prompt_cache_key`，
   跨协议发射时一并带过去（Chat 与 Responses 都已支持这个字段）。

两处都只是「路由提示」，按设计不改变输出语义，因此**不记降级**。

### 验证

新增两个回归用例：

* `routing::sticky::tests::anthropic_metadata_session_id_is_a_strong_identity`
  ——同一会话换用户消息绑定不变，换会话必须换键。
* `tests/protocol_fidelity.rs::the_anthropic_session_id_carries_over_as_an_openai_cache_hint`
  ——Messages→Chat / Messages→Responses 都保留 `prompt_cache_key`，且保真度为 Lossless。

`cargo fmt --check` 干净；`cargo test` 全绿（lib 533 项 + 全部集成用例）。

### 上线后怎么验收

按分组看 `sticky_origin` 的构成，`cache_key` 应当成为 Messages 流量的大头：

```sql
select group_id, sticky_origin, count(*)
from request_records
where protocol = 'anthropic_messages'
  and http_status = 200
  and started_at > strftime('%s', 'now') - 86400
group by 1, 2 order by 3 desc;
```

再看这些分组的缓存命中率是否随之抬升（对照改前几天的均值）。

## 二、sub2api：OpenAI 分组在 Claude Code 下 403

### 结论

**不是 Akhub 的问题，是 sub2api 分组的两个开关各自只开了一半。** 两个报错来自两条
互斥的路径，同一个分组里不可能同时满足：

| 现象 | 触发条件 | 代码位置 |
|---|---|---|
| `403 This group does not allow /v1/messages dispatch` | 分组 `allow_messages_dispatch = false` | `handler/openai_gateway_handler.go` 的 `allowOpenAICompatibleMessagesDispatch` |
| `400 ... does not allow cross-protocol conversion` | 分组 `cross_protocol_conversion_enabled = false` | `service/cross_protocol_conversion.go` |

### 现场证据

```
groups：26 GPT-不降智混合缓存 → dispatch=t, cross=t   ✅ 两个都开，能用
        33 GPTPro不降智       → dispatch=f, cross=t   ❌ 403
        27 ccmax (anthropic)  → dispatch=f, cross=f
```

`ops_error_logs` 里 20:50 与 20:55 各有一次 403，全部来自 **group 33 的 key 52**：

```
102398  2026-11-18 20:50:43  group=33  ak=52  403  /v1/messages
102405  2026-11-18 20:55:13  group=33  ak=52  403  /v1/messages
```

再往上追 `audit_logs`，能看到 20:54 那两次保存**把开关踩回去了**：

```
20:51:38  GPTPro不降智  dispatch=true   cross=true
20:54:01  GPTPro不降智  dispatch=true   cross=false   ← 跨协议关了
20:54:40  GPTPro不降智  dispatch=false  cross=true    ← 调度也关了
```

两次 PUT 之间只隔 39 秒，是同一个编辑弹窗里连改两下、分别保存。

### 为什么「两个都开也无效」要分开看

- **group 33 现在 dispatch 是关的**，所以一定 403。把「允许 /v1/messages 调度」打开
  即可消除 403。
- 打开之后才会走到**第二条**检查：如果这个账号没有原生 Anthropic 端点，就必须要
  「允许 Anthropic 协议族 ↔ OpenAI 协议族互转」。group 33 的 cross 已经是开的，
  所以**这个分组只要把 dispatch 也打开就够了**。
- 两个开关的语义并不重叠：dispatch 管「这个 OpenAI 分组能不能接 /v1/messages 进来」，
  cross 管「进来以后，账号没有原生端点时能不能转协议兜底」。只开一个必然卡住。

### 第二个报错：`gpt-6-astra[1M]` —— 这其实是 sub2api 的真 bug

一开始判断成「客户端自己弹的」：最初那条日志确实落在 group 27（anthropic 平台），
模型列表里没有 `gpt-6-astra`。但把 group 33 的 dispatch 打开后复测，**404 依旧**：

```
model=gpt-6-astra      → HTTP 200
model=gpt-6-astra[1M]  → HTTP 404  not supported by any configured account
model=gpt-6-astra[1m]  → HTTP 404
```

**根因**：`[1m]` 的归一化只挂在 `ParseGatewayRequest` 上，而它只被 **Anthropic 原生入口**
调用。OpenAI 兼容入口 `OpenAIGatewayHandler.Messages`（openai/composite 平台的
`/v1/messages`）**根本不走那条路**，于是带后缀的模型名原样进了 `model_mapping` 查找，
必然 miss → 404。`normalizeClaudeCodeLongContextModel` 在这个入口上是死代码。

**修法**：把这个入口也接上同一个归一化函数（不新写第二份逻辑），并把改写后的模型名
写回请求体；原始的带后缀写法留给 `return_requested_model` 回显。

```go
// handler/openai_gateway_handler.go（openai 兼容 /v1/messages 入口）
clientModel := reqModel
if normalized := service.NormalizeClaudeCodeLongContextModel(reqModel); normalized != reqModel {
    reqModel = normalized
    body, _ = sjson.SetBytes(body, "model", reqModel)
}
```

服务端加一层导出包装（唯一实现仍在 `service` 里）：

```go
func NormalizeClaudeCodeLongContextModel(model string) string {
	return normalizeClaudeCodeLongContextModel(model)
}
```

补丁存档：`/opt/sub2api-app/patches/1m-suffix-fix.patch`。

### 建议的动作（已执行）

1. **group 33** `allow_messages_dispatch` 已置 `true`（与 group 26 一致）。
   注意别在同一弹窗里连改两个开关分别保存——20:54 那次两个 PUT 互相覆盖，
   正是这次 403 的直接来源。
2. **cross_protocol_conversion_enabled** 保持 `true`（账号没有原生 Anthropic 端点时
   才需要它，group 33 没有原生端点）。
3. **`[1m]` 后缀**：已修在网关侧，客户端带不带都能用。
