## 本次改动（12 项修复）

### 请求记录与可观测

1. **`config_version` 改为入口捕获**。旧实现在结算时才读当前配置版本，一次请求
   可能跑两百多秒、跨过多次配置变更，现场（10-25 09:15–09:18）同一秒内并存的
   记录带着 v=2 与 v=3 交错，事后无法判断某条请求是哪份配置产生的。

### 配置改了不生效

2. **改分组排队容量后不生效**。`GroupQueues::semaphore()` 只在表里没有该分组时
   才用传入的 capacity 建信号量，已存在就原样返回——参数被静默丢弃。调大仍按
   旧的小上限拒（`queue_full`），从「不限」收回则根本收不回来，只有重启才恢复。
   改为 `QueueSlot` 自己记额定容量并按配置校准；缩容只回收空闲名额。
3. **清空并发上限后限制永不消失**（`Budget::configured()` 从校准结果反推，
   与 `effective_limits()` 回填构成自反馈环）。**本次未修**，理由见下文。

### 状态不回收

4. **托管后台任务 handle 泄漏**。`spawn` 早于 `register`，快速失败的任务在登记
   之前就跑完并调了 `finish`，那个 id 再也删不掉；客户端对它的 cancel 会谎报
   「已中断上游连接」。
5. **Key 级动态状态永不清理**。`live_credential_ids()` 生产 0 调用者，轮换掉的
   Key 留下永不消失的 `KeyState`；攒到上限后随机淘汰，可能抹掉**正在使用**的
   Key 的熔断，已知坏的 Key 重新上岗。
6. **备份恢复后内存实时汇总不重建**（`LiveStats::clear()` 无调用者），成本页会
   按恢复前的账号显示当日用量。

### 并发正确性

7. **排队唤醒后拿 A 的 Key 级名额去用 B**。`capacity_any_key` 抢到的是某一把
   Key 的名额，唤醒后重新抽签可能选中另一把，直接接管会让 B 的 Key 级上限被
   绕过、A 的名额被白占。
8. **目标级半开名额被无关请求清掉**。三个 settle 分支用无条件
   `release_half_open()`，会把别人后来抢到的试运行名额抹掉——「熔断后只放行一个
   真实试运行」被打破，且失败时退避等级不增长。
9. **倍率表单账号写入的读改写丢更新**。定时轮与后台「立即刷新」并发时，后写的
   覆盖前一次，先写入账号的新倍率与清掉的 `stale_since` 回退成旧值。

### 其它

10. **启动恢复漏掉 30 秒宽限期内的遗留任务**，永远停在 `queued`（最长挂到保留期）。
11. **成本页「还能再省多少」用错基准**，从不读记录里的反事实倍率；流量没落到最便宜
    目标上时节省恒为 0，把真实优化空间吞掉。
12. **v18 重建会静默丢弃旧库的未知列**，改为拒绝启动并点名是哪一列。
13. **登录失败计数表可被任意 `username` 撑大**，加 4096 上限。

### 未修的一条（需要先定语义）

**清空并发上限后限制永不消失**。`Budget::configured()` 从**已校准的信号量容量**
反推配置值，而 `effective_limits()` 在调用方没提并发时又拿它回填——两者构成自
反馈环：清空之后每次准入都从上次校准取回旧上限再校准回去。

没修的原因：要修它必须同时决定「调用方没提并发」表示「沿用上次」还是「这一级
不限」，而既有用例 `admission_honours_an_already_calibrated_target_cap` 断言的
正是自反馈环的行为本身。这是产品语义取舍，不该在发版前顺手拍板。

生产影响：**当前为零**——生产库中 `limit_concurrency` 在账号、目标、Key 三级
全部为 `NULL`（实测 0/0/0），这条路径不会被触发。
