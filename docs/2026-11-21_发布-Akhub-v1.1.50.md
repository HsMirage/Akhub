# 发布 Akhub v1.1.50：客户端断开后读完上游再计费（§26.3 修订）

## 这次修的是什么

现场（req_01M7Y760MFGD5SMVHVYPBERDN4）：

| 位置 | 记录 |
|---|---|
| Akhub | 「未知 / 未知 输出用量未知 · 未完成统计」，`error_code=client_gone` |
| sub2api | 输入 2,503 / 输出 126 / 缓存 47.5K（95% 估算） |
| New API | `流状态: 错误 client_gone`，输入 49,517 / 输出 178 |

三方各说各话。根因不在统计口径，而在**上游流被提前丢掉**：

1. 终端客户端断开 → sub2api 取消请求 → Akhub 侧响应体被 axum 丢弃；
2. v1.1.49 把上游流的读取写在响应体（`async_stream` 生成器）里，body 一丢，
   生成器连同上游连接一起没了；
3. 而上游此刻还在正常生成——那部分真实用量我们永远读不到，上游却照记自己的账。

所以 v1.1.48 补的「异常结束也补发计费终止帧」只在**上游先出错**时有效；
**下游先走**这条路上，我们连用量都没有，补帧也无从补起。

## 改法：读取与结算搬进独立任务

`settle_stream` 拆成两半：

- `pump_upstream`（`tokio::spawn`）持有上游流、累计用量、负责结算落库；
- `downstream_stream` 只从 channel 取字节转给下游。

客户端断开时，下游那半被丢弃只是让 channel 关闭，pump 继续把上游读完（drain），
拿到真实 usage 后再按 `client_gone` 结算。

### 收手的时机

drain 不能无限等，否则这次请求的记录会一直被推迟——记录页看不到调用，比少记
一点用量更糟。两道闸：

- `client_gone_drain`（默认 60 秒，可配 0 关闭）：断开后的总时长上限；
- drain 阶段实际等待上限取 `min(client_gone_drain, 1 秒)` 的墙钟预算：
  上游真空闲就立刻收手。

另有一条快速退出：断开时上游**一个字节都没送出**（纯心跳，现场 opus-5-5 那种
首字百秒级慢回答），drain 读不到任何用量，立即结算。

### 结局判定

保持 v1.1.49 已有的语义，只加一个判据 `unfinished_at_disconnect`：

- 断开那一刻上游**已经**送出终止信号 → 记 `Completed`（回答完整送达，需求证据）；
- 断开那一刻还没送出 → 记 `client_gone`（即便 drain 后来补到了收尾）。

这样「drain 回来的用量」不会被误读成一次正常完成。

### 保留不变

- 错误帧之前先补 usage-only 帧、错误之后补协议终止帧（v1.1.48 的行为）；
- 缓存并入输入价、不带缓存细分（与上游 New API 同口径）；
- 图片端点不补终止帧：它的 usage 就挂在 `image_generation.completed` 上；
- 超时路径同样补终止帧（`stream_timeouts` 用例覆盖）。

## 测试

- 新增 `a_client_disconnect_still_drains_the_upstream_for_real_usage`：
  上游在断开**之后**才发 usage，断言记录里的输入/输出用量被读回来且标 `client_gone`。
- 新增夹具 `Behavior::StreamUsageAfterRelease` 复现"断开时上游还在生成"的形状。
- 全量 920 个测试在编译机通过，`cargo clippy --all-targets -- -D warnings` 与
  `cargo fmt --check` 干净。

## 平台

沿用 v1.1.48 起的策略：只发 `linux-x86_64` 与 `windows-x86_64`，不发 arm64。

## 升级提示

新增设置项 `client_gone_drain`（默认 60 秒）。断开后多读一小段上游会**略微增加
上游开销**（上游会把这一轮生成完），这是换取"按上游口径计费"的必要代价；
不想付就把该项设为 0，行为退回 v1.1.49。
