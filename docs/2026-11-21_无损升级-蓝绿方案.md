# Akhub 无损升级（蓝绿）

## 为什么需要

同一台机、同一份 compose、同样的命令，升级停机时间却差很多：

| 版本 | 停机 |
|---|---|
| v1.1.47 | 1 秒 |
| v1.1.48 | 59 秒 |
| v1.1.49 | 53 秒 |
| v1.1.50 | 87 秒 |

根因不是命令不同，而是 `docker compose up -d` 的顺序是**先停旧、再起新**。
旧容器里有在途的长流式请求，它必须等这些流结束才能退出
（`stop_grace_period: 200s`）。v1.1.47 那次的 1 秒，只是恰好没有在途长流。

只要"停旧"与"起新"解耦，在途流就一条都不用断。

## 拓扑约束

Akhub 有两个入口，切换必须都覆盖：

| 调用方 | 地址 |
|---|---|
| sub2api | `http://89.58.17.138:8088`（宿主端口） |
| new-api | `http://akhub:8080`（Docker 内网容器名，16 条渠道） |

端口绑定在容器创建时固定，无法热改；容器名别名同理。所以需要一层**常驻的
转发层**，它自己不动，只改指向：

```
             ┌──────────────┐
调用方 ──────▶│ socat :8088  │──┬──▶ akhub-blue  :18088
             └──────────────┘  └──▶ akhub-green :18089
```

socat 只做 TCP 转发，不解析 HTTP，SSE 原样透传（已实测）。

## 一次性改造

```bash
scp scripts/bluegreen.sh akhub-origin:/opt/akhub/bluegreen.sh
ssh akhub-origin 'chmod +x /opt/akhub/bluegreen.sh && /opt/akhub/bluegreen.sh'
```

改造内容：

1. 停旧容器，按新拓扑在 blue 槽（:18088）起当前版本；
2. `docker-compose.yml` 里 `8088:8080` 改成 `127.0.0.1:18088:8080`；
3. socat 常驻监听 8088，转发到 blue。

改造本身有一次停机（约 5-10 秒）。**改完之后 new-api 需要改渠道地址**：
把 `base_url=http://akhub:8080` 的 16 条渠道改成 `http://89.58.17.138:8088`
（已验证 new-api 容器可以访问宿主 IP）。不改也能用，但那些渠道不走 socat，
切换时会被截断。

## 之后的每次升级

```bash
/opt/akhub/bluegreen.sh 1.1.51
```

流程：

1. 拉镜像；
2. 在**空闲槽位**以只读方式挂载数据、起新版本（预热，不影响生产）；
3. 健康检查通过后，把 socat 指向新槽位 —— **切换在这里，毫秒级**；
4. 新槽位转为可写正式运行；
5. 旧槽位摘掉网络、继续跑完在途长流，跑完自动删除。

在途长流一条不断。

## 数据安全

Akhub 是单实例设计（无进程锁，粘性绑定、性能统计、会话都在内存里），
两个实例同时写同一份 SQLite 会互相覆盖快照。所以：

- 新槽位在**切换前一律只读挂载**（`:ro`），只读不写；
- 切换是把"唯一写者"从旧槽位交给新槽位，不是长期双写；
- 旧槽位在切换后立刻摘掉网络别名，不再接新请求。

## 回滚

```bash
/opt/akhub/bluegreen.sh --rollback   # 切回上一个槽位（秒级）
/opt/akhub/bluegreen.sh --status     # 看当前槽位与版本
```

## 风险

- 切换瞬间在途长流会在新容器里重新建立不了（TCP 连接是绑到旧槽位的），
  但**旧槽位不会立刻死**，它跑完才退场，所以已经建立的流不受影响。
- 只影响**切换那一刻新建立**的连接：socat 重启的几百毫秒内可能有连接被拒。
  实测可接受；如果要更平滑可换成 nginx stream（需装 `libnginx-mod-stream`）。

## 不用蓝绿时的快速替换

如果只是想少等一会儿、接受截断长流：

```bash
/opt/akhub/upgrade-fast.sh 1.1.51     # 默认最多等 5 秒排空
DRAIN_SECS=30 /opt/akhub/upgrade-fast.sh 1.1.51
```
