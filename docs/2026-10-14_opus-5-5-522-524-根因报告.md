# opus-5-5 经 CDN 报 522 / 524 根因报告（首字前零字节沉默）

- 排查时间：2026-10-14 14:00 → 16:00（北京）
- 报障原文：`https://ai.hsnb.fun` 使用 opus-5.5 报 **522**；`https://ai-cf.hsnb.fun` 使用 opus-5.5 报 **524**
- 源站：89.58.17.138（德国 Vienna，nginx 1.26.3）
- 前置报告：[2026-10-09_新建令牌522-根因报告.md](2026-10-09_新建令牌522-根因报告.md)、[2026-10-10_EdgeOne-522-复核与近端回源方案.md](2026-10-10_EdgeOne-522-复核与近端回源方案.md)

## 一、结论

**524 已在本机稳定复现，根因不是 CDN，而是 Akhub 在"上游首个语义事件到达之前"一个字节都不发给下游。**

- Akhub 的流式响应要等到嗅探器看到**语义事件**（Anthropic 的 `message_start` / `ping` 不算）
  才构造并下发 HTTP 响应头。上游在那之前沉默多久，CDN 就等多久。
- opus-5-5 的首字延迟（TTFT）本身就在 **17–230 秒**量级，且 2026-10-14 05:00 UTC 起进一步恶化。
- Cloudflare 的"源站响应超时"约 **100 秒**：等不到任何字节就回 **524**。
- 实测复现：同一个 6.8 MB 请求，EdgeOne 侧 76 秒后返回 **200**，Cloudflare 侧 **129.9 秒后返回 524**。

**522 与 524 不是同一个触发点，但同源。**

- 524 = Cloudflare 的**源站响应超时**（源站首字前沉默 > ~100s）。
- 522 = EdgeOne 的**回源建连失败**。EdgeOne 对"源站响应慢"极有耐心（源站 nginx 日志里有
  EdgeOne 持有连接 **300.7 秒**才关闭的记录），所以 522 不是响应超时，而是
  「边缘 → 德国源站」的 **TCP 建连**在劣化时段超过 EdgeOne 的源站连接超时（约 5s）——
  这正是 2026-10-09/10 两份报告已定位的机制。本次新增的放大器是：
  **opus-5-5 的请求会挂 100–400 秒**，每个长挂请求占住一条 EdgeOne → 源站的连接，
  建连压力与重试风暴同时上升，522 因此更容易被撞上。

## 三、代码定位（为什么一个字节都不发）

### 3.1 同协议流式：响应头推迟到首个语义事件

`src/gateway/passthrough.rs:2837-2868`：

```rust
let started = Instant::now();
let mut response = response;
let mut sniffer = stream::Sniffer::new(downstream);
loop {
    match response.chunk().await {
        Ok(Some(chunk)) => match sniffer.push(&chunk) {
            stream::Verdict::Pending => continue,          // 还没语义内容：继续等
            stream::Verdict::Semantic => {
                let prefix = sniffer.take_buffer();
                let body = translate::passthrough_stream(prefix, response, downstream, forward.request_id);
                return Ok(Success { status, streamed: true,
                    response: build_response(forward, status, &headers, prepared, body), ... });
            }
            ...
        },
        ...
    }
}
```

`build_response` 只在这一刻才被调用（`src/gateway/passthrough.rs:3428`）。在此之前
`attempt_inner` 没有返回，axum 也就没有下发任何响应头。跨协议路径同理
（`src/gateway/translate.rs:74-155`，`commit_stream` 的 `loop { response.chunk().await }`）。

### 3.2 嗅探器的判据

`src/gateway/stream.rs:197-204`：

```rust
fn anthropic(event: Option<&str>, payload: Option<&serde_json::Value>) -> Verdict {
    match event_kind(event, payload) {
        Some("message_start") | Some("ping") => Verdict::Pending,
        Some(_) => Verdict::Semantic,
        None if payload.is_some() => Verdict::Semantic,
        None => Verdict::Pending,
    }
}
```

`message_start` 与 `ping` 都被判为"还没开始"，于是**连上游的心跳都不转发**。
上游在首个 `content_block_delta` 之前沉默多久，下游就沉默多久。

### 3.3 空闲超时管不到这一段

- `src/gateway/passthrough.rs:1366-1367`：`idle_timeout` 只在**流提交之后**生效
  （由 `settle_stream` 逐块计时，`src/gateway/settle.rs:136-149`）。
- 提交之前只有总超时兜底：`request_timeout` 默认 **600 秒**
  （`src/app/mod.rs:50`、`src/main.rs:55`），而 Cloudflare 只给 100 秒。
- `src/gateway/passthrough.rs:493`：`let deadline = forward.started_at + settings.request_timeout;`

**600 秒的容忍度与 100 秒的 CDN 之间没有任何缓冲层。**

- 05:00 UTC（13:00 北京）起首字延迟断崖式恶化，>100s 的请求从个位数跳到每小时 23–47 条。
- 这些记录 `attempts` **恒为 1**、`queued_ms` 与 `sticky_wait_ms` **恒为 0**、
  `upstream_status=200`：慢在"上游首字之前"，不是 Akhub 排队，也不是重试。
- `first_token_ms ≈ duration_ms`（例：`dur=153843ms ft=148707ms`），
  说明 Akhub 在整段等待里没有向下游发出任何东西。

  first_token 124–405 秒。

## 五、EdgeOne 侧：522 为什么不是"响应超时"

源站 nginx 访问日志里有这样的记录：

```
222.79.117.157 - - [14/Oct/2026:07:58:33 +0200] "POST /v1/messages?beta=true HTTP/1.1" 499 0 \
  rt=300.713 urt=300.713 ust=- host=ai.hsnb.fun xff="117.61.84.166"
```

**EdgeOne 持有这条回源连接 300.7 秒**才放弃。这与本次实测（沉默 75.9 秒仍返回 200）一致：
EdgeOne 的源站**响应**超时远长于 Cloudflare 的 100 秒。

所以 522 只能来自**建连阶段**：

- 2026-10-09/10 的定位：劣化时段「边缘 → 89.58.17.138:443」的 TCP 建连超过约 5s 即回 522；
  坏边缘 POST 稳定 5.10–5.26s 返 522，且那些 POST **从未到达源站**。
- 本次新增的放大器：opus-5-5 的请求会挂 100–400 秒，每条都占住一条
  EdgeOne → 源站的连接；客户端等不到又重试，进一步推高建连需求。
- 源站侧未见饱和（见下），所以瓶颈仍在跨境建连那一段。

源站体检（2026-10-14 06:34 UTC）：`ss -s` Total 231 / estab 34；443 上 established 16；
`TcpExtListenOverflows 0`、`TCPBacklogDrop 0`、`TCPAbortOnMemory 0`；
`/var/log/nginx/error.log` **0 行**；akhub 容器 cpu 0.02% / 692.9 MiB。
`TcpExtEmbryonicRsts 9510`、`TcpExtSyncookiesSent 976` 与"边缘放弃连接并 RST"一致。

## 六、处置

### 6.1 代码修复（本次已实施）：首字前心跳

**改法**：给"等首个语义事件"这一段加预算。预算内等到语义事件 → 维持原行为（仍可切换目标）；
预算耗尽 → **立刻下发响应头**，并在继续等待上游首字期间**每 N 秒发一个 SSE 注释帧
（`: keep-alive`）**。注释帧是 SSE 规范的一部分，所有客户端与 Akhub 自己的嗅探器都忽略它
（`src/protocol/sse.rs:16`、`src/gateway/stream.rs:79-82`），因此不影响语义边界。

这样 CDN 看到的是「≤ 预算的沉默 + 每 N 秒一个字节」，而不是「100 秒以上零字节」。

**代价（必须知道）**：一旦预算耗尽、响应头下发，这次尝试就**不能再切换目标**——
§13.3 本来就规定"上游只是慢、没有明确失败"不切换，所以这与设计一致；
但确实放弃了"沉默很久之后才报错"这一类场景的切换机会。绝大多数可切换失败
（连接失败、明确的 4xx/5xx、立即到达的错误帧）都发生在预算之内，不受影响。

### 6.2 运维动作（本次未做，需你执行）

1. **香港近端回源中转至今没有部署**：`47.76.54.171` 上 `systemctl is-active nginx` = **inactive**，
   而 `deploy/edgeone-relay/` 在 2026-10-10 就已交付。这是 522 的正解，建议尽快执行
   `deploy/edgeone-relay/setup-relay.sh` 并在 EdgeOne 控制台切源站。
2. EdgeOne 控制台若可调「源站连接超时」，从约 5s 上调到 15–30s 作为兜底。
3. Cloudflare 侧的 524 阈值不可调（免费/Pro 计划），只能靠 6.1 的心跳绕开。
