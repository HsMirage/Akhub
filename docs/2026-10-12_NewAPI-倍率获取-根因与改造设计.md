# New API Key 倍率获取 — 根因与改造报告

**日期**：2026-10-12
**问题**：ccmax 分组的「冰峰-ccmax」账号填了访问令牌 + 用户 ID，刷新出的倍率是 **1X**，
实际应为 **0.85x**。用户补充观察：「第一次填写为 newapi 时不会默认按 newapi 格式处理；
保存后再点开这个账号才能获取分组信息」。

---

## 一、结论先说

这不是"取不到倍率"，而是**取错了分组**，外加一条独立的**保存前拿不到分组**的体验缺陷。
两个缺陷叠加，恰好把 0.85 显示成 1。

| # | 缺陷 | 位置 | 症状 |
|---|---|---|---|
| A | 分组解析跳过"令牌分组"，直接对整张矩阵取 `max()` | `src/multiplier/probe.rs`（旧 `new_api`） | 取到错误档位 |
| B | 新建时无法拉分组（按钮禁用），首次倍率是前端补的占位值 1 | `web/src/pages/Accounts.tsx` | 保存后要等一轮刷新才对 |

---

## 二、缺陷 A：为什么是 1X

### New API 的真实计费链（逐字核实）

**relay 计费按「令牌分组」走**——令牌自己绑了分组时，它覆盖用户的默认分组：

```go
// new-api/middleware/auth.go:345-362（TokenAuth）
userGroup := userCache.Group
tokenGroup := token.Group
if tokenGroup != "" {
    ...
    userGroup = tokenGroup            // ← 令牌分组覆盖用户分组
}
common.SetContextKey(c, constant.ContextKeyUsingGroup, userGroup)
```

**最终倍率**：

```go
// new-api/relay/helper/price.go:19-46
userGroupRatio, ok := ratio_setting.GetGroupGroupRatio(relayInfo.UserGroup, relayInfo.UsingGroup)
if ok {
    groupRatioInfo.GroupRatio = userGroupRatio      // 专属倍率优先
} else {
    groupRatioInfo.GroupRatio = ratio_setting.GetGroupRatio(relayInfo.UsingGroup)
}
```

**未知分组静默回落 1**：

```go
// new-api/setting/ratio_setting/group_ratio.go:84-91
func GetGroupRatio(name string) float64 {
    ratio, ok := groupRatioMap.Get(name)
    if !ok {
        common.SysLog("group ratio not found: " + name)
        return 1                       // ← 这里就是那个 1X
    }
    return ratio
}
```

**而 `/api/user/self/groups` 返回的倍率是按「用户分组」算的**：

```go
// new-api/controller/group.go:26-46
userGroup, _ = model.GetUserGroup(userId, false)        // ← 用户分组，不是令牌分组
...
usableGroups[groupName] = map[string]interface{}{
    "ratio": service.GetUserGroupRatio(userGroup, groupName),
}
```

### 旧实现的错法

拿到整张矩阵后取最高档：

```rust
// 旧 src/multiplier/probe.rs
None => data.values()
    .filter_map(|raw| group_ratio(raw).ok())
    .max()                                  // ← 与"我这把 Key 属于哪一档"无关
    .context("New API 返回的分组中没有一个带合法倍率")?,
```

用户分组若不在 `group_ratio` 表里，New API 对未知分组回落到 **1**，界面就显示 1X。

### 实测数据（2026-10-12，newaicxy.xyz）

```
$ curl -s https://newaicxy.xyz/api/user/groups
{"ccmax":{"desc":"无限制可蒸馏","ratio":0.85},
 "heavy-grok":{"ratio":0.2}, "kiro个人号按次":{"ratio":0.28},
```

## 三、缺陷 B：保存前拿不到分组

- `Accounts.tsx:907`：新建时 `multiplier_mode` 默认 `manual`。
- `Accounts.tsx:1433`（旧）：「拉取分组」按钮 `disabled={... || !account}` —— **新建态直接禁用**。
- 后端 `account_multiplier_groups` 必须有已落库账号，且要求 `multiplier_mode == NewApi`。
- 于是新建时 `new_api_group` 必然为空 → 保存后 `Entry::pending` 用 `manual_multiplier` 顶着，
  前端留空补 `"1"` → **列表显示 1 并带「已过期」徽标**。
- 后台刷新 5 分钟一轮 + 0–25% 抖动，最坏 **6.25 分钟**才首次探测。

## 四、Cockpit 是怎么做的（已独立复核）

**结论：Cockpit 并不获取 New API 的倍率。** 没有可照抄的实现。

复核方式（本机只读扫描）：

| 目标 | `api/user/self/groups` | `New-Api-User` | `group_ratio` | `ratio_config` | `multiplier` | `倍率` |
|---|---|---|---|---|---|---|
| `jlcodes.antigravity-cockpit` 2.1.26 / 2.1.28 / 2.1.29 的 `out/extension.js` | 0 | 0 | 0 | 0 | 0 | 0 |
| `/Applications/Cockpit Tools.app`（Tauri，v1.3.67） | 0 | 0 | 0 | 0 | — | — |

- VS Code 扩展是 Google Antigravity 配额监控器，只打 `cloudcode-pa.googleapis.com` 等 Google 域名。
- Cockpit Tools 取的是**额度/余额**（`total_granted` / `total_available` / `hard_limit_usd` …），
  走 `/api/cockpit-tools/token-profile`，不是倍率。
- **唯一可借鉴的是 Base URL 处理**：真 URL 解析 → 只接受 http/https → `set_path` 丢弃 `/v1`
  → `set_query(None)` → `set_fragment(None)`。Akhub 的 `probe_url` 已经等价（且更保守：
  只剥末段正好是 `v1` 的那一层）。

## 五、其他能获取 New API Key 倍率的方法

按"能否反映**这把 Key 实际生效的倍率**"排序：

| # | 方法 | 鉴权 | 评价 |
|---|---|---|---|
| 1 | `GET /api/token/search?token=sk-...` → `items[].group` | 访问令牌 + `New-Api-User` | ✅ **这把 Key 自己绑的分组**，正是 relay 计费用的分组。服务端用完整 Key 精确匹配（自动剥 `sk-`），返回的 `group` 是明文 |
| 2 | `GET /api/user/self` → `data.group` | 同上 | ✅ 令牌没绑分组时的生效档位（正常状态） |
| 3 | `GET /api/user/self/groups` | 同上 | ⚠️ 按**用户分组**算的矩阵；只有配合 1/2 才能定位正确档位 |
| 4 | `GET /api/log/token`（用 Key 自己调） | 仅该 Key | ✅ **实际发生值**（`other.group_ratio` / `user_group_ratio`），但依赖已有消费记录 |
| 5 | `GET /api/pricing` → `group_ratio` | 无 / session | ⚠️ 全站表；用访问令牌调**拿不到**用户级覆盖（`TryUserAuth` 只读 cookie session） |
| 6 | `GET /api/user/groups` | **部分站点无鉴权** | ⚠️ 只有"组名 → 倍率"，不含归属。实测 newaicxy.xyz / ai.hsnb.fun / wzw.pp.ua 可用 |
| 7 | `GET /api/ratio_config` | 无（站长可关，默认关） | ❌ 实测 403「倍率配置接口未启用」，且无分组维度 |

**Akhub 采用了 1 + 2 + 3 的组合**（4 需要已有消费记录，不适合做实时倍率来源；
5/6 无法回答"我是哪一档"）。

## 六、改了什么

### 后端

1. **四级分组解析**（`src/multiplier/probe.rs`）——逐级降级，绝不猜低：
   1. 账号上显式填的 `new_api_group`：取不到就报错，绝不静默换档；
   2. 令牌自己的分组（`/api/token/search`）；
   3. 用户默认分组（`/api/user/self`）；
   4. 可用分组最高档（保守兜底）。

   第 2、3 步是**尽力而为**：老版本没有这些路由或站点限流时降级，**不让整轮刷新失败**
   （拿不到准确档位 ≠ 拿不到倍率）。

2. **无状态预览** `POST /admin/api/new-api/preview-groups`：保存前就能拉分组、解析档位。
   凭据只用于这一次请求，不落库、不回吐（有测试断言）。

3. **建号/改号立刻插队探测**：把首次倍率从最坏 6.25 分钟压到一次 tick（10 秒）内。

4. **倍率来源可见**：`multiplier_group` / `multiplier_group_source` 随账号返回，
   提示语按实际取值生成（不再写死"没填分组就用最高档"）。

### 前端

- 「拉取分组」在新建态可用（走预览接口），不再要求"先保存再点开"。
- 自动选中解析出的分组，并显示「已识别：这把 Key 实际落在「ccmax」，倍率 0.85（来自 Key 自身绑定的分组）」。
- 已选过分组时不覆盖管理员的选择。

## 八、限制

1. **`group_group_ratio`（用户级专属倍率）没有公开端点**。当"令牌绑了分组 + 该用户对它有专属
   倍率"时，纯 API 合成会有偏差；只有消费日志能给出 100% 精确值。当前实现取
   `/api/user/self/groups` 里该分组的比值，对绝大多数站点正确。
2. **`auto` 分组是黑盒**：真实分组由渠道可用性逐请求决定，任何静态方法都无法预知。
   `/api/user/self/groups` 对 `auto` 返回字符串 `"自动"`（非数字），当前实现会把它当作
   无合法倍率而跳过——不会误当成某个具体档位。
3. **只能查自己的令牌**：`/api/token/search` 强制 `user_id = 本人`，所以"站点级凭据 + 别人的
   Key"这种组合解析不出分组，会走保守兜底。
4. 上游版本差异：解析链依赖 `/api/token/search` 与 `/api/user/self`，两者在本次核对的
   fork（HEAD `bee7e20b2`）与 upstream 上一致；老版本缺失时会降级而非报错。
