## 过程记录：一次被 SSH 断线打断的 recreate

第一次 `docker compose up -d` 通过 SSH 前台执行时，命令在 **recreate 的中途**
被会话超时打断（本会话的 SSH 有约 2 分钟硬上限）。后果是：

* 旧容器 `akhub:1.1.27` 已停止、进程已退出，但容器对象还在（`unhealthy`）；
* 新容器 `c8442491c571_akhub` 只创建未启动（`Created`）；
* 端口 8088 只剩 `docker-proxy`，实际后端 `Connection refused`——**服务中断约 3 分钟**。

恢复方式（也是以后该用的方式）：把 deploy 放进 `setsid nohup` 里跑，让它在服务器上
脱离 SSH 会话自行完成。

```bash
setsid nohup bash -c 'docker rm -f <orphan>; docker compose up -d --no-deps akhub' \
  </dev/null >/tmp/deploy-1128.log 2>&1 &
```

这条经验已写进 `/opt/akhub/README.md` 的升级步骤，避免下次再踩。

## 核心修复的生产验证

`key_id` / `key_label` 此前**从未写入**（升级前 0/133,878）。新版运行后开始落库，
并据此第一次可以按 Key 归因缓存：

```
=== 同一账号 + 同一前缀的 Key 稳定性（新版运行期间）===
  acct=CYN56E in=   4387 n=1 [H] 同一把 ✓
  acct=H3Q6SE in= 278566 n=1 [H] 同一把 ✓
  acct=H3Q6SE in= 278884 n=2 [HH] 同一把 ✓
  acct=H3Q6SE in= 279460 n=1 [H] 同一把 ✓
  acct=V3MHGN in=   4387 n=2 [HH] 同一把 ✓

  汇总：同前缀同 Key 5 组 / 换 Key 0 组
  全部请求：6/6 = 100% 缓存命中
```

样本量还小（新版刚上线数分钟），但**换 Key 次数为 0** 正是本次修复的目标行为——
修复前，绑定的那把 Key 只要并发满就会被静默换掉。

## 限制

* 观察窗口短（数分钟、6 条请求）。缓存命中率的真实改善需要按天看——修复前
  hyper 的 21 Key 池命中率 67.8%，全库同前缀基线 93.1%。
* 生产上尚未出现"绑定那把 Key 并发满"的现场，所以 `BoundBusy` 的等待路径是
  由单元/端到端测试覆盖的，不是生产观测到的。
* 首次 recreate 造成约 3 分钟服务中断，属操作失误而非版本缺陷。
