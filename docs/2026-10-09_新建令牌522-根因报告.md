# 新建令牌 522 根因报告（腾讯 EdgeOne 边缘回源超时）

- 排查时间：2026-10-09 21:00 → 2026-10-10 01:00（北京）
- 源站：89.58.17.138（德国纽伦堡，你叫它 HSNB/新 API 面板机）
- 触发问题：用户在新 API 面板 `/keys` 点"新建令牌"时报 `Request failed with status code 522`

## 一、结论

522 是**腾讯 EdgeOne 边缘节点**返回的（响应头 `server: TencentEdgeOne`、`content-length: 0`、带 `eo-log-uuid`），**不是源站 / Akhub / New API 产生的**。

机制：

1. EdgeOne 有一批中国大陆边缘节点 → 德国源站的**回源链路劣化**：健康边缘端到端 POST 往返 0.7–1.1s，劣化边缘的回源往返要 **5–6s**。
2. EdgeOne 的"源站连接超时"约 **5s**（522 稳定在 5.10–5.26s 返回）。
3. 需要**新建回源连接**的请求（POST `/api/token/`，即"新建令牌"）撞上该超时 → **522**；而 GET 类请求可以复用已建立的回源长连接 / 命中边缘缓存，仍能成功（只是慢 5–6s）。
4. 这正好解释用户的主观体验：**面板能打开（GET 慢但成功），一"新建令牌"就 522**；同时因为只有部分省份的边缘节点坏，表现为"很多人（但不是所有人）报错"。

抽样 19 个大陆边缘节点，**4 个坏（约 21%）**：

| 坏边缘 IP | DoH-ECS 解析归属 | 症状 |
| --- | --- | --- |
| 114.237.67.63 | 江苏南京 | POST → 522/5.1s，GET → 200/5.3–5.9s |
| 61.170.82.52 | 上海 / 杭州 | 同上 |
| 117.69.71.130 | 湖北武汉 / 安徽合肥 | 同上 |
| 1.71.87.196 | 山东济南 | 同上 |

其余 15 个边缘（深圳 58.251.87.142、河南 123.6.40.77、福建 124.72.129.118、广东 211.97.84.91、36.249.95.107、湖南/天津/陕西/四川/云南等）POST 均 401、0.7–1.1s，正常。

## 二、证据链

1. **源站侧清白**：15 天 531,423 行 nginx 访问日志里**没有任何 52x**；error.log 15 天仅几 KB（只有 Akhub 重启时的 4 条 `recv() failed (104)`）；ListenOverflows 0、conntrack 305/262144、并发 <20；到达源站的真实 POST /api/token/ 70 条里 69 条 200。
2. **从大陆节点复现**（阿里云深圳 120.24.253.211）：
   - 用 AliDNS DoH + EDNS Client Subnet 模拟 20 个省市客户端解析 `ai.hsnb.fun`，收集到 19 个 EdgeOne 大陆边缘 IP；
   - 对每个边缘 IP `curl --resolve ai.hsnb.fun:443:<边缘IP>` 发 POST /api/token/：**15 个 401（0.7–1.1s）、4 个 HTTP/2 522（5.1s，TencentEdgeOne）**，5/5 必现，两个时间段复测一致；
   - 坏边缘再做分级测试：GET `/`、`/index.html`、`/static/css/...`、`/api/status`、`/api/user/self` **全部 200**（耗时 5.3–19.9s），**只有 POST → 522**。
3. **稳定性复测**：对上述 4 个坏边缘 + 2 个健康边缘做 4 分钟一轮的连续监控（2026-10-09 16:46/16:51/16:55 UTC 三轮，此前 16:33 的 sweep 亦同）：坏边缘**每一轮都是 522**（5.11–5.26s），健康边缘每一轮都是 401（0.4–1.0s）→ 该回源劣化是**持续性**的，不是瞬时抖动。
4. **源站日志交叉验证**：19 个带唯一 tag 的 POST 中**只有 15 个到达源站**（正好是 15 个健康边缘），4 个坏边缘的 POST **从未到达源站**（TCP 连接根本没建起来）；而同一批坏边缘的 GET（带 tag）确实到达源站并 200。→ 失败点在"边缘 → 源站"的连接建立阶段。
4. **回源出口映射**（源站 `remote_addr`）：EdgeOne 大陆边缘的回源出口就是之前被我误判为"直连客户端 TOP5"的那些 IP，例如 123.6.40.77→114.66.250.60、58.251.87.142→116.163.46.188、36.249.95.107→36.250.238.254、211.97.84.91→36.248.57.28、112.28.174.246→223.109.0.243。
5. **Cloudflare 路径**（ai-cf.hsnb.fun / ai.cakepool.top）从大陆看也不稳，但不是本次 522 主体：POST 12 次中 11 次 401 但耗时 0.9–13.4s、1 次 45s 无响应；TTFB 尾部 6.9–9.2s；TLS 0.44–5.09s。

## 四、建议处理（按优先级）

1. **拿 eo-log-uuid 提腾讯云工单**（uuid 见第五节）：请腾讯查这几个边缘节点到 89.58.17.138:443 的回源链路，并确认/上调"源站连接超时"（现在约 5s，正是 522 的触发阈值）。
2. **给 EdgeOne 配近端回源（最有效的根治办法）**：用你已有的香港/东京机器（47.76.54.171 香港、43.128.225.152 / 8.211.163.172 东京）做一层反向代理，EdgeOne 回源到香港/东京（RTT 几十 ms），再由中转机走稳定线路到德国；或在 EdgeOne 源站组里配置多个源站地址 + 健康检查。
3. **临时兜底**：让华东用户改用 `ai-cf.hsnb.fun`（Cloudflare 路径 POST 基本能通）。
4. **源站侧加固**（与 522 无直接因果，但建议做，均已定位到具体位置）：
   - new-api / cliproxy 容器加内存上限：10-08 11:19:51 与 11:20:11 两次内核 OOM 就是这两个容器里的 `grep` 吃到 7.5GB；
   - 删除 `/etc/nginx/sites-enabled/newapi.conf.bak-20260927-060134`（导致 `conflicting server name "ai.hsnb.fun"` 告警被忽略）；
   - nginx `log_format` 增加 `$host $request_time $upstream_response_time $http_x_forwarded_for`，下次可直接定位 CDN 回源问题；
   - `worker_connections 768 → 4096`。
