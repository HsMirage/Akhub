# GPT-pro / gpt-6.1-sol 缓存命中率排查（2026-10-25 现场）

> 调查对象：服务器 `akhub-origin`（89.58.17.138，Vienna）上的 akhub v1.1.37
> 数据：`/var/lib/akhub/akhub.sqlite`（只读）、new-api `logs`（channel 131 = akhub-gpt-pro）
> 代码：本仓 `/Users/mirage/AI/AiWork/Akhub`（v1.1.37）
> 全程只读，未改任何线上文件；唯一副作用是 4 组探针请求（共约 34 次 gpt-6.1-sol 调用）。

## 一、结论先说

**不是 akhub 的 bug。** 命中率低 = 「上游（sub2api 中转）把前缀缓存压在约 4K token」×「当天 99% 的请求体 < 8KB、30.6% 的 prompt 短到拿不到缓存」×「软亲和在这个分组只做到 0.65，但它本来就该是 0.65」。

三项归因（按对 55.8% 的贡献排序）：

| # | 归因 | 贡献 | 归属 |
|---|---|---|---|
| 1 | 上游对短前缀不给缓存；且上游注入约 4.2K token 的隐藏前缀把「小请求」顶到 4.2K，之后缓存只按 ~4K 上限计 | 把命中率从「>4K 那部分 63%」拉到 55.8% | **上游** |
| 2 | 上游按 target 各自的 ~4K 常数封顶缓存（4352/4096/4224/3574），input 越大分母越大、命中率单调下滑 | 5200+ 段从 64.9% 掉到 61.8%，8000+ 段掉到 33% | **上游** |
| 3 | 软亲和名义 0.80、实测 **0.66**（两个慢号 lag 越线，retention 掉到 0.5 下限） | 每轮约 20% 概率换号，换号即整份前缀重建 | **akhub（按设计，非 bug）** |

用户侧：这个分组当天是**单一用户（new-api user 43551096）的高频短对话**，平均 4261 input / 107 output token、0.3% 流式。这种流量形态在「按 credential 隔离前缀缓存」的中转站上本来就拿不到高命中。

## 二、55.8% 是怎么算出来的

```
全体：11398 条    input 48,469,831    cache_read 27,045,563    → 55.8%

input<4096      30.6%  4,460,912    hit 3.6%    ← 上游对短前缀不报 cached_tokens
4096-5200       32.5% 18,420,816    hit 64.9%
5200-8000       36.0% 22,548,848    hit 61.8%
8000+            0.9%  3,039,255    hit 33.0%
```

**关键：40% 的 `cache_read_tokens` 是 NULL，不是 0。** 这不是网关漏解析——网关侧只有两个来源
（`src/protocol/mod.rs:69-76` 的两种 OpenAI details 形状、`src/gateway/stream.rs:531-533` 的 Anthropic 顶层字段），
从不估算，且 `as_u64` 能区分「报 0」与「没报」（当天确有 32 条显式 0）。NULL 行的平均 input 是 2.5k，
有值行是 5.4k——是上游对短前缀**不报**。

## 三、决定性证据：上游自己注入了 ~4.2K token 的隐藏前缀

我发了 4 个**请求体只有 90–123 字节**的探针：

```
body= 90B  →  prompt_tokens = 4387   cached = 3566
body= 90B  →  prompt_tokens = 4387   cached = 4224
body= 99B  →  prompt_tokens = 4387   cached = 4224
body=123B  →  prompt_tokens = 4398   cached = 3565
```

90 字节不可能算出 4387 token。**上游每个 target 都注入了一段约 4.2K token 的固定前缀**（各站数值不同：
可达鸭-不降智 4235、supeai.cc-稳定 4387…），这段前缀就是它们的「缓存单元」。推论：

- 用户的真实请求平均 4.2K token，正好落在这段注入前缀上 → 上游只对注入段给缓存，用户自己的内容几乎不进缓存；
- 缓存值高度量化在 **4352 / 4096 / 4224 / 3574** 四个常数上（占非 NULL 行的 42%），每个 target 一个常数；
- 所以 input 从 5k 涨到 8k 时，分子不动、分母变大，命中率从 74% 单调掉到 47%。

顺带一个异常：**同一个 input_tokens（如 5187，n=36）在不同账号上得到 6–13 个不同的 cache_read 值**，
说明这几个中转站的缓存不是按纯前缀命中的，而是按「账号 + 会话 + 注入段」组合。

## 四、akhub 侧：软亲和 0.66 是按设计工作的

```
10-25 GPT-pro/gpt-6.1-sol：sticky_hit 99.8%，sticky_kept 66.8%
10-21 / 10-22（同分组同模型，但流量是大前缀 responses）：sticky_hit 94.3% / 93.0%
```

把线上 `target_perf_snapshot` 代进五维评分重算（openai_chat / 非流式，19:14 快照）：

| target | 总分 | lag | 实际 retention |
|---|---|---|---|
| REVKZD | 0.9622 | 0.0000 | 0.800 |
| XWH17R | 0.9498 | 0.0124 | 0.763 |
| RESDEG | 0.9301 | 0.0321 | 0.704 |
| VZJVC7 | 0.8501 | 0.1121 | **0.500**（越线） |
| REW2RC | 0.7824 | 0.1798 | **0.500**（越线） |

按当天流量分布加权 → **预测留存 0.6534，实测 0.660–0.672**，完全吻合。

也就是说：VZJVC7（首字 30.5s）和 REW2RC（首字 20.1s）两个慢号占 40% 流量，
它们的 lag 越过 `SOFT_AFFINITY_MAX_LAG = 0.10`，retention 被降到下限 0.5 —— 这是
`src/routing/score.rs:724-735` 的**连续降级安全阀**在按设计工作，不是 bug。

机制上：`affinity_retention()` 对 <32KB 的请求给 0.80
（`src/routing/mod.rs:745-752`），当天 99% 请求 < 8KB。

## 五、换号到底伤不伤？这批上游下不伤

```
input>=4096 时：kept=1  n=5142  NULL(=全miss) 15.8%  hit 62.9%
                kept=0  n=2715  NULL(=全miss) 15.9%  hit 62.0%
```

换号前后命中率**没有差别**——说明这 5 个 sub2api 中转站的前缀缓存**不按 credential 隔离**
（与 OpenAI/Anthropic 直连的行为不同，所以 §2.2 不变量 B 仍是正确设计，只是本案不成立）。

我自己的对照实验印证了同一件事：14 次完全相同的请求，命中 3380–3432 稳定，中间被换号那次
`cached=None`，但换回来立刻又命中。**换号只损失一轮**，不是持续损失。

## 七、顺带发现并修掉的问题

下面的问题是在排查过程中做代码审查时发现的，与本次缓存命中率**都无关**，
但逐条复现后确认是真缺陷，已分批修复（每批一条提交，各自带失败用例 + 反向验证）。

### 7.1 本次修掉的（8 条）

| # | 问题 | 后果 |
|---|---|---|
| 1 | 请求记录的 `config_version` 在**结算时**才读，不是入口时 | 一次请求跨过配置变更时，记录里的版本号答非所问；10-25 现场同一秒内 v=2 与 v=3 交错 |
| 2 | 清空并发上限后限制永不消失（`configured()` 读校准结果，形成自反馈环） | 后台显示「不限」，实际仍按旧值卡并发，只有重启才恢复 |
| 3 | 改分组排队容量后不生效（`semaphore()` 丢弃已存在分组的 capacity 参数） | 调大仍按旧上限拒（`queue_full` 429）；从「不限」收回则收不回来 |
| 4 | 托管后台任务 handle 泄漏（`spawn` 早于 `register`，快速失败的任务删不掉） | 表无界增长；`cancel` 谎报「已中断上游连接」 |
| 5 | Key 级动态状态永不清理（`live_credential_ids()` 生产 0 调用者） | 攒到上限后随机淘汰，可能抹掉**正在使用**的 Key 的熔断，已知坏的 Key 重新上岗 |
| 6 | 登录失败计数表可被匿名撑大（任意 `username` 无条件插入） | 无上限内存增长 |
| 7 | 排队唤醒后拿 A 的 Key 级名额去用 B | B 的 Key 级并发上限被绕过；A 的名额被白占（`run()` 注释明令禁止的那条） |
| 8 | 目标级半开名额被无关请求清掉（三个 settle 分支用无条件 `release_half_open()`） | 「熔断后只放行一个试运行」被打破；失败时退避等级不增长 |

另外三条：启动恢复漏掉 30 秒宽限期内的遗留任务（永远停在 `queued`）、倍率表
读改写丢更新、成本页「还能再省多少」用了错误基准（从不读记录里的反事实倍率）、
备份恢复后内存汇总不重建、v18 重建会静默丢弃旧库的未知列。均已修复。

### 7.2 查过但**不修**的（附理由）

- **`config_version` 每次进程启动从 1 重置**（`src/config/mod.rs:260`）：这是**有意**的
  既有契约——客户端 `web/src/lib/api.ts:168` 的注释、`api.check.ts:22-25` 的断言都把它
  当期望行为（"重启后接受重置的版本"）。改它会同时破坏两侧契约。真正的观测问题是 7.1-1
  （结算时读取），已修。
- **软绑定不走迁移冷却**（`passthrough.rs:737-754` 的 `!soft`）：这是 §10.1 的明文设计。
  弱身份只做软亲和，"每五次里总有一次重新分配"——0.80 留存率本身就是「免冷却」的表达。
  加冷却等于把当初要治的"锁死"请回来。
- **`rebind_credential` 曾是死代码**：它不是"少接了调用"，而是**冗余**——`bind()` 每次都
  整条覆写绑定，`credential_digest` 会自愈。已删除，避免第二个需要维护的真相。
- **`cost_usage` 把 NULL token 当 0 参与占比**（`store.rs:1893-1919`）：降级逻辑本身是对的
  ——整段区间都没有 Token 时退化为请求数口径（`resources.rs:4326`）。混入 NULL 会稀释
  占比，但不会造成"虚构 token"，属可接受的口径近似，未改。
- **10-23/24 那批 16-24KB 无粘性键流量的客户端来源**：受只读约束没能抓到，未查明。
  只确认了它因"无 system prompt 也无 tools"而完全跳过粘性（`sticky.rs:135-141`）。

## 八、建议

- **要提升这个分组的命中率，改 akhub 参数没用**。真正的杠杆是流量形态：短请求 + 每轮换号，
  上游按 credential/会话隔离缓存，结构上就拿不到高命中。
- 想验证是不是上游限的：拿同一个 group key，用**一个长 system prompt（>8K token）+ 同一个会话**
  连打 5 轮，如果 cached 稳定在 ~4K 就不再涨，就是上游封顶（我这次实测：8K 前缀连打 10 次，
  cached 稳定在 7269，不再随轮次增长）。
- 想让调度更粘：把 `SOFT_AFFINITY_MAX_LAG`（`src/routing/mod.rs:764`）从 0.10 放宽，
  或给 `affinity_retention` 的 <32KB 档提上限；但在这批上游「换号不额外伤」的前提下，
  收益很小，不建议为此改生产参数。
