# 账号内 Key 池设计（§4.2 修订）

> 文档状态：需求已确认，作为 `计划.md` 的补充设计，进入实施。
>
> 更新日期：2026-09-21
>
> 背景：同一个上游平台下往往有几十把 API Key。按现在的模型，每把 Key
> 都要建一条独立账号记录，倍率、优先级、模型选择集、限额都要重复配置
> 一遍，账号列表会被同质条目淹没。本设计让**一个账号容纳多把 Key**，
> 并在这些 Key 之间复用网关已有的调度、健康与粘性能力。

## 一、要解决的问题与红线

三个需求，按优先级排列：

1. **一次配置，多把 Key。** 一个账号填多把 Key，不必为每把 Key 建账号。
2. **Key 之间也要负载均衡。** 复用账号之间已有的那套：加权随机、粘性、
   熔断冷却、半开试探、并发与 RPM/TPM 限额、健康徽标。
3. **切换 Key 不能打断缓存亲和。** 这是最硬的一条约束。

第 3 条值得单独解释。上游的 prompt cache 在**几乎所有实现里都是按
「凭据 + 前缀」隔离的**：换成另一把 Key，即使 Base URL 和模型完全相同，
前缀缓存也是冷的，一次 100K 上下文的重建成本约等于缓存读价的 20 倍。
因此"Key 池"如果实现成"每个请求随机挑一把 Key"，它省下的配置工作会被
缓存重建的账单吃回去。**本设计把 Key 绑定提升为与目标绑定同等重要的
调度状态。**

## 二、三条不可协商的不变量

### 2.1 不变量 A：一次下游调用只使用一把 Key

从下游请求进入网关到返回响应，中间只允许出现一把 Key。同一请求内的
故障转移、重试、跨协议转换都不得换 Key——**Key 只在决定"这次调用归谁"
的那一刻选定一次**。

这条不变量有两个收益：请求记录里的凭据归属是明确的；响应状态链（§15）
与上游资源（`resp_xxx`）天然绑在同一把 Key 上。

### 2.2 不变量 B：缓存亲和优先于层内评分

粘性绑定（§10）绑定的对象从"调度目标"升级为"调度目标 + Key"。

- 粘性命中时，Key 的选择**不是再抽一次签**，而是直接使用绑定里的那把。
- 只有绑定的 Key 不再合格（停用、熔断、额度耗尽、限额满且超出等待预算、
  被管理员删除）时，才在同一账号内换 Key 并在绑定里改写。
- 层内评分的加权随机只在"这一次调用还没有任何绑定"时决定用哪把 Key。

换句话说：**已建立的会话永不因为"另一把 Key 分数更高"而迁移。**

### 2.3 不变量 C：Key 级状态与账号级配置分层

| 归属层级 | 内容 |
|---|---|
| 账号级（所有 Key 共享） | 上游类型、Base URL、协议与自适应、人工优先级、倍率模式与校准系数、模型选择集与别名、隐藏原始模型、账号总限额、健康摘要 |
| Key 级（各自独立） | 凭据本身、启用开关、标签、Key 级限额覆盖、熔断/冷却/半开、额度耗尽状态、Key 失效状态、RPM/TPM 窗口、并发额度 |

这条分层的直接后果是：**账号的倍率、优先级、分层与模型目录不因为多 Key
而改变**。多 Key 不产生新的层、不产生新的倍率、不产生新的模型。

## 三、数据模型

### 3.1 新表 `upstream_account_keys`

```sql
CREATE TABLE IF NOT EXISTS upstream_account_keys (
    id                TEXT PRIMARY KEY,
    account_id        TEXT NOT NULL REFERENCES upstream_accounts(id) ON DELETE CASCADE,
    -- 后台展示用的标签。留空时界面按序号显示"Key 1"。
    label             TEXT NOT NULL DEFAULT '',
    -- XChaCha20-Poly1305 密封后的凭据，与 upstream_secrets 同一套密封格式。
    sealed_key        BLOB NOT NULL,
    -- 明文凭据经主密钥 pepper 派生的摘要（hex）。
    -- 用途只有一个：让健康与粘性状态在"同一把 Key 重新加密"后仍然对得上。
    -- 换个 nonce 重新 seal 同一把 Key，密文会变，摘要不会。
    credential_digest TEXT NOT NULL,
    -- Key 级限额覆盖，NULL 表示继承账号。语义与调度目标的覆盖完全一致（逐项）。
    limit_rpm         INTEGER,
    limit_tpm         INTEGER,
    limit_concurrency INTEGER,
    enabled           INTEGER NOT NULL DEFAULT 1,
    created_at        INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_account_keys ON upstream_account_keys(account_id, created_at);
```

### 3.2 兼容列

`upstream_secrets` 增加：

```sql
ALTER TABLE upstream_secrets ADD COLUMN keys_migrated INTEGER NOT NULL DEFAULT 0;
```

`api_key` 列**保留**，并且继续作为"第一把 Key"的镜像写入。这样：

- 旧二进制打开新库时仍能读出凭据（不会因为结构版本检查被拦住——版本号由
  `SCHEMA_VERSION` 管理，见 §3.4）。
- 恢复旧备份、以及任何还没改到 Key 表的代码路径都仍然可用。

### 3.3 请求记录与尝试明细

`request_attempts` 增加 `key_id` 与 `key_label`：多 Key 之后，"这次尝试
用哪把 Key"是排查问题的第一现场，"换了几个目标"已经不足以回答。

`request_records` 增加 `key_id`：这次请求最终落在哪把 Key 上。

> **凭据本身绝不落任何记录。** 记录里只出现 Key 的内部 ID 与管理员的标签，
> 与 §23.4、§24.1 既有的"不记录 Header、Key、正文"一致。

### 3.4 迁移（SCHEMA_VERSION 9 → 10）

1. 建 `upstream_account_keys` 表与索引。
2. `upstream_secrets` 补 `keys_migrated` 列。
3. 对每个 `keys_migrated = 0` 且 `api_key` 非空的账号：用主密钥解开
   `api_key`，作为**第一把 Key** 写入新表（标签默认空、启用、无覆盖限额），
   计算 `credential_digest`，置 `keys_migrated = 1`。
4. 迁移必须在**应用层**做而不是纯 SQL：第 3 步需要主密钥解密。它放在
   `storage::open` 之后、`ConfigService::load` 之前的一次性步骤里，
   按 `keys_migrated` 判断幂等。

**失败语义**：单条账号解密失败（主密钥换过、密文损坏）时，该账号标记为
"无可用 Key"并在后台如实显示，绝不让进程起不来——一个账号的凭据坏了不该
拖垮整台网关。

## 四、凭据池（明文只存在于内存）

### 4.1 为什么不每次解密

现在的 `load_api_key` 每次尝试都做一次 SQLite 读 + 一次 AEAD 解密。单 Key
时这点开销可以忽略（本地库、单条主键查询），但多 Key 之后**每次请求还要
决定用哪把**，而"决定"需要先知道有哪些 Key、各自的限额与摘要。把这些信息
做成一份不可变快照，热路径就退化成一次内存查表：

```rust
pub struct CredentialPool {
    // 账号 ID → 该账号的 Key 池快照
    accounts: HashMap<String, Arc<AccountKeys>>,
}

pub struct AccountKeys {
    pub account_id: String,
    /// 按 `created_at, id` 稳定排序，保证同样的配置得到同样的抽签顺序。
    pub keys: Vec<Arc<AccountKey>>,
}

pub struct AccountKey {
    /// 内部 ID，稳定且不含凭据内容。健康状态、粘性绑定与请求记录都用它。
    pub id: String,
    pub account_id: String,
    pub label: String,
    pub enabled: bool,
    /// 对账号限额的逐项覆盖。
    pub limits: Limits,
    /// 明文凭据。只在内存，绝不进日志、绝不落库、绝不进 API 响应。
    pub secret: Arc<str>,
    /// 明文摘要（hex），用于让健康状态跨重新加密保持稳定。
    pub credential_digest: String,
}
```

快照随配置版本一起原子替换（`ArcSwap`），与 `RuntimeConfig` 同一套
语义：在途请求持有旧 `Arc`，不会读到一半新一半旧的 Key 池。

### 4.2 明文内存的边界

- 只在 `Runtime` 内持有，生命周期与进程一致（与主密钥、`Cipher` 同级）。
- 不进 `RuntimeConfig` 的 `Debug` 输出（`AccountKey` 手写 `Debug`，
  只打印 ID 与标签）。
- 不进备份、不进审计日志、不进错误信息。
- 账号被删除或 Key 被删除时，随下一次快照替换一起消失。

### 4.3 健康状态的键

健康、粘性与请求记录引用 Key 时统一使用 **`(account_id, credential_digest)`**
派生的稳定串，而不是 `id`：

- 管理员"改一下标签"不该丢掉熔断状态。
- 管理员把同一把 Key 重新粘贴一遍（换 nonce 重新 seal）也不该丢掉。
- 真正换了一串凭据（digest 变了）时，旧状态自然对不上，被 `retain` 清掉——
  这正是我们要的语义：换了一把坏 Key 就该重新开始。

## 五、Key 选择与调度位置

### 5.1 阶段划分

Key 选择插在**候选目标已经确定之后、真正发请求之前**：

```
分组 → 逻辑模型 → 硬性资格过滤 → 分层 → 层内加权随机 → 选中目标
                                                      ↓
                                            ★ 在选中目标的账号内选 Key
                                                      ↓
                                            端点选择 → 发请求
```

这样排的理由：账号与目标是已有的调度单元（分层、评分、粘性都长在这一层），
Key 是**目标内部的凭据细分**。让 Key 参与分层会给系统引入第二种"层"，
与 §9.2 的严格阶梯互相打架；让 Key 完全不参与又达不到负载均衡的目的。
放在目标内部，Key 只影响"同一个账号的流量怎么摊到几把凭据上"。

### 5.2 选择算法

```
select_key(account, pinned, sticky_hint):
    候选 ← 账号内 enabled 的 Key
    候选 ← 过滤掉不可用的（Key 失效 / 额度耗尽 / 冷却 / 并发满 / RPM·TPM 满）

    1. pinned 在候选里            → 用它            // 不变量 B
    2. sticky_hint 在候选里        → 用它            // 换绑后沿用同一把
    3. 候选非空                    → 按加权随机抽一把
    4. 候选为空但存在"忙"的 Key     → 返回 Busy，交给已有的排队路径
    5. 候选为空且全都是"坏"        → 返回 Unavailable(账号级原因)
```

第 3 步的权重来自 `score::Registry`：**Key 复用目标级性能统计**，不新增
一套统计维度。理由是"同一个目标、不同 Key"的性能差异主要来自凭据本身的
配额与限流，而那已经由健康状态精确表达了；再叠一层 EWMA 只会让择时变慢、
让统计样本被稀释。

### 5.3 抽签必须可测

随机源与 `routing::plan` 一样从外部注入（`&mut impl FnMut() -> f64`），
测试因此可以断言"同一条前缀永远回到同一把 Key"、"两把 Key 的分配比例
随权重变化"，而不是靠统计跑一百次。

## 六、健康与准入：账号 → Key → 目标

### 6.1 三级准入

`health::AdmissionLimits` 从两级扩为三级，逐级收紧：

```rust
pub struct AdmissionLimits {
    /// 账号总额度：账号内所有 Key 共享的闸门。
    pub account: Limits,
    /// Key 覆盖：在账号额度的基础上再收紧（逐项覆盖）。
    pub key: Limits,
    /// 目标覆盖。
    pub target: Limits,
}
```

有效限额 = `账号限额.overridden_by(Key 覆盖).overridden_by(目标覆盖)`，
与 §17.1 既有的逐项覆盖语义完全一致。

### 6.2 状态粒度

| 现象 | 影响范围 |
|---|---|
| 401/403 Key 失效 | **该 Key**；账号内其他 Key 不受影响 |
| 429 / 额度耗尽 | **该 Key**（额度是按凭据计的） |
| Key 级 RPM/TPM/并发 | **该 Key** |
| 账号总并发/RPM/TPM | 账号（所有 Key 共享） |
| 5xx、连接失败、损坏响应 | 目标（既有语义不变） |

这条修正很重要：现在 §12.1 把 401 记为"整个账号"失效。多 Key 之后，
一把 Key 被上游封了不该让另外九把 Key 一起停摆——那是把 Key 池的全部
价值抵消掉。**单 Key 账号的行为完全不变**（唯一那把 Key 失效 = 账号失效）。

### 6.3 半开试探移到 Key 级

半开名额（§12.3）从账号移到 Key：一个账号最多同时试一把坏 Key，不会出现
十把 Key 一起放试探流量打上游的情况。

## 七、网关路径：Key 级故障转移

### 7.1 换 Key 重试

当一次尝试因为**凭据级原因**失败时，同一个账号内换一把健康 Key 重试：

| 失败原因 | 处理 |
|---|---|
| 401 / 403（Key 失效） | 该 Key 硬停；换 Key 重试 |
| 429 且带 `Retry-After` | 记该 Key 限流；粘性请求先按 §10.3 原地等待，超预算才换 Key |
| 额度耗尽 / 账号封禁 | 该 Key 冷却；换 Key 重试 |
| 连接失败、5xx、超时、协议损坏 | **不换 Key**，按既有语义换目标 |

### 7.2 与尝试预算的关系

§13.1 的尝试预算是按**代价**计的：一次连接都没建立的失败是廉价失败，
不计入预算。换 Key 属于同一类廉价失败，但必须设上限，否则一个账号里
50 把全是坏 Key 时，一次下游请求会打出 50 次上游尝试。

新增常量：

```rust
/// 一次请求针对同一个目标最多换几次 Key（§13.1 的失控保护）。
pub const MAX_KEY_SWITCHES_PER_TARGET: usize = 3;
```

超过上限即视为"这个目标不可用"，按既有语义换目标。

### 7.3 可观测性

- 每次换 Key 都写入 `request_attempts`（含 `key_id` / `key_label`），
  所以"这次请求换了三把 Key 才通"在请求记录里一目了然。
- 流式请求在首字之前换 Key 是安全的（上游尚未开始生成）；首字之后不可能
  再换（§13.4 的"已开始生成即不可切换"不变）。

## 八、各子系统的适配

### 8.1 响应状态链（§15）

`response_states` 增加 `key_id`。原生生命周期代理（`retrieve` /
`input_items` / `cancel` / `delete`）必须用**创建这条响应时的那把 Key**，
因为 `resp_xxx` 在上游是凭据隔离的资源。

链式续写请求同样钉住那把 Key（不变量 A）：

- 记录里的 Key 仍然合格 → 强制选它，不抽签。
- 记录里的 Key 已被删除/停用 → 该链按"不可续写"处理，返回明确的错误码，
  **不静默换 Key**。换 Key 续一条链在上游必然 404，静默重试只会把真正的
  原因藏起来。

### 8.2 倍率探测（§11.2）

- **Sub2API**：`/v1/sub2api/billing` 是 **Key 级**接口，因此逐 Key 探测，
  账号的有效倍率取**所有 Key 里最高的那个**（保守口径：宁可低估余额，
  也不能因为挑了一把便宜的 Key 就放行一个实际更贵的请求）。任一 Key
  探测失败都记入账号的倍率错误信息。
- **New API**：`/api/user/self/groups` 是**用户级**接口，需要访问令牌 +
  用户 ID，与推理用的 `sk-xxx` 是两套凭据。**不随 Key 数变化**，行为不变。

### 8.3 模型发现与同步（§16.1）

`GET /v1/models` 用**第一把启用的 Key**；401/403 时依次换下一把，全部失败
才报错。模型列表本身是站点/用户级的，不存在"每把 Key 一套模型"的语义，
所以不逐 Key 拉取。

### 8.4 复制账号与测试连接

- **复制账号**：整个 Key 池一起复制，每把 Key 用新 nonce 重新密封
  （与既有的"两条记录绝不共享密文"一致，§20.4）。
- **测试连接**：逐 Key 测试，返回每把 Key 的结果。这是多 Key 之后最有用的
  一个诊断动作——"哪几把 Key 已经死了"应该一次就能看出来。

### 8.5 备份与恢复（§23.5）

- 导出：`backup_account_keys` 输出 `{id, account_id, label, api_key(明文),
  limits, enabled, created_at}`。备份整体已被备份口令加密，与既有
  `secrets` 的处理一致。
- 恢复：用本机主密钥重新密封并重算 `credential_digest`。
- **旧备份**（没有 Key 池）恢复时，把 `secrets` 里的单把 Key 展开成
  一把 Key 的池；**新备份**恢复进旧二进制时，`upstream_secrets.api_key`
  仍然写入第一把 Key，旧二进制照常工作。

## 九、后台界面与 API

### 9.1 账号抽屉

「API Key」单行输入框换成 Key 列表：

```
API Key
  ┌──────────────────────────────────────────────────────┐
  │ #1  [生产主号............]  [限额▾]        [测试] [×] │
  │ #2  [备用-东八区..........]  [限额▾]        [测试] [×] │
  │ + 添加一把 Key                                        │
  └──────────────────────────────────────────────────────┘
  额度按凭据计：Key 出问题只影响它自己，其他 Key 继续服务。
  同一个会话始终落在同一把 Key 上，不会打断上游的前缀缓存。
```

- 已保存的 Key **不回吐明文**（§23.2 不变）：列表里显示标签 + 摘要前缀 +
  健康状态。要换就整把重新粘贴。
- 每把 Key 可展开设置 Key 级 RPM / TPM / 并发覆盖。
- 标签留空时界面按序号显示。

### 9.2 账号列表

- 「Key」列显示 `3 把 / 1 把异常`，异常时徽标取最严重的那把 Key 的状态。
- 账号级健康摘要（`AccountHealthDto`）增加 `keys` 数组，逐把 Key
  给出状态与原因。

### 9.3 REST API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/api/accounts` | 每个账号带 `keys` 数组（无明文） |
| POST | `/admin/api/accounts` | 请求体用 `keys: [{label, api_key, limits?}]`；为兼容旧的 `api_key` 字段，单独给 `api_key` 时等价于一把 Key |
| PATCH | `/admin/api/accounts/{id}` | `keys` 整体替换（有 ID 的复用、无 ID 的新增、缺失的删除）；也接受单独的 `api_key` |
| POST | `/admin/api/accounts/{id}/test` | 逐 Key 测试，返回每把 Key 的结果 |

> **整体替换的语义是刻意的**：Key 池是"一组凭据"而不是"一组可独立编辑的
> 实体"，整体替换让界面与服务端的认知不会漂移，也天然支持拖拽排序。

## 十、边界与失败语义

| 情形 | 行为 |
|---|---|
| 账号有 0 把启用的 Key | 该账号的所有目标不合格，原因 `没有可用的 Key`；账号健康摘要显示 `no_key` |
| Key 池为空（从未配置） | 与上面相同；后台在账号行明确提示 |
| 同一把 Key 在一个账号内重复粘贴 | 允许，但后台给出提示——重复的 Key 不会带来额外额度，只会让熔断状态分裂成两份 |
| 同一个 Key 出现在两个账号里 | 允许（既有语义允许"同一个真实 Key 放进两个分组"） |
| 一整个账号的所有 Key 都失效 | 账号级健康摘要显示 `key_invalid`，与单 Key 时的表现一致 |
| 管理员删掉响应链正在用的 Key | 该链返回明确错误，不静默换 Key（§8.1） |

## 十一、测试

新增 `tests/account_keys.rs`，全部通过真实 HTTP 打到可编排的假上游：

1. **单 Key 回归**：只有一把 Key 的账号，行为与改造前逐项一致（含粘性、
   熔断范围、限额）。
2. **Key 轮换**：无粘性的短请求在 10 次调用里两把 Key 都用到（同一前缀的
   请求全部落在同一把 Key 上）。
3. **缓存亲和**：带相同 system prompt 的 20 次请求全部命中同一把 Key，
   即使另一把 Key 的健康度更差/更好都不迁移。
4. **换 Key 重试**：Key A 返回 401 时，同一次下游调用改用 Key B 成功返回，
   下游只看到一次成功；`request_attempts` 里出现两条记录、Key 不同。
5. **Key 级熔断隔离**：Key A 熔断期间，账号内所有请求走 Key B，
   账号整体不进入冷却。
6. **Key 级限额**：Key A 设 `max_concurrency = 1` 时，并发请求溢出到 Key B。
7. **响应链钉 Key**：`previous_response_id` 续写回到创建该响应的那把 Key。
8. **迁移**：v9 库（单 Key）升级后，凭据仍可用、Key 池有一把 Key、
   摘要非空。
9. **备份往返**：多 Key 账号导出再导入后，Key 数量、标签、限额与凭据
   全部保持，且密文不重复。
10. **换 Key 上限**：三把坏 Key + 换 Key 上限 3 时，一次下游请求打出的上游
    尝试次数不超过上限。

## 十二、明确不做（本期边界）

- **不做"跨账号共享 Key 池"。** Key 池属于账号；同一个 Key 想放进两个分组
  仍然要复制成两个账号（§4.2 不变）。
- **不做 Key 级倍率。** 倍率是账号级安全状态（§11 的前提），Sub2API 的
  Key 级读数只用于取账号口径的最保守值。Key 级倍率会让"分组倍率上限"
  这条红线失去唯一口径。
- **不做 Key 级模型目录。** 上游的模型列表是站点/用户级的。
- **不做 Key 级性能 EWMA 分表。** 理由见 §5.2。
- **不做 Key 权重。** 权重来自评分与健康状态；人工调 Key 排序等价于
  调整优先级，那属于账号层。

### 顺带修掉的两个真实缺陷

1. **无限额度的层级仍然把并发当资源发**：三级各自持有一个信号量，但只有配置了
   上限的层级才会真正参与抢占与排队，否则「账号跑满」会把「Key 还有名额」一起
   挡住。
2. **取消准入不归还并发容量**：`cancel_before_upstream` 只退限流计数，信号量
   名额靠 permit 析构归还、额定容量却没有补回。反复的"预扣 → 取消"会把容量
   越削越小，最后同级请求全都拿不到名额。

### 修复记录（本轮收尾）

#### 1. 三个排队用例的回归

根因是**额度解析分散在三处**：准入、排队、资格检查各自把"调用方没提并发"解释
成不同的东西。具体地，排队走 `Registry::capacity`，而它只按调用方传入的
`Limits` 决定要不要盯某一级的信号量——调用方传的是 `Limits::default()`，
于是**满载的目标信号量根本没被纳入等待集合**，等待者只能看到账号那一级，
一有账号名额就被立刻唤醒，绕过排队直接降层。

定案口径（用户确认）：**账号内的 Key 之间等价于账号之间，应用完全相同的处理
逻辑；一个账号能填多个 Key 只是为了解决配置复杂**。据此把额度解析收敛成一处
`effective_limits`，三处共用：

- 准入 `admit`：决定扣多少、开哪个信号量；
- 排队 `capacity`：决定等哪一级的名额；
- 资格检查 `check`：判断忙不忙。

同时把 `reconcile_capacity` 的语义定死为"只抬不降"：`None` 表示调用方对此
没有意见，保持现状，绝不重置成"不限"。

#### 2. Key 级状态的归类键传错

资格检查把 Key 的**行 ID** 当成归类键传给健康层，而准入用的是**凭据摘要**。
两者不一致意味着资格检查查的是一个永远新鲜的 `KeyState`，多 Key 账号的熔断
与限额在准入之前形同虚设。修正后归口到同一份定义（`credential::credential_id`）。

这条修正在验收里暴露了第二个问题：资格判定原来**只看池里第一把 Key**，于是
"第一把刚好熔断"会让整个目标退出候选，而同账号里健康的 Key 一把都用不上——
恰好是 Key 池要解决的问题本身。现在的语义是"任意一把通过硬性检查就算这个目标
合格"，全部失败时优先报"忙"（可排队）而不是"坏"。

#### 3. `#[ignore]` 的用例已恢复

`a_busy_lossless_target_is_not_bypassed_by_degraded_traffic` 不再跳过：改成
**两个候选账号都占住**并发名额，这样无论同层抽签抽到谁，无损候选都是"忙"，
用例不再随抽签结果飘。

#### 4. 前端 Key 池编辑器

`web/src/components/KeyPoolEditor.tsx`：逐把 Key 的标签、明文、启用开关与
独立限额；已保存的 Key 显示摘要前缀与健康徽标，明文永不回显（"留空则不变"）。
账号列表新增 "Key" 列（`2/2`、`未配置`、`N 把异常`）。新增行必填明文、
限额必须为正整数，校验不过会拦住保存。
