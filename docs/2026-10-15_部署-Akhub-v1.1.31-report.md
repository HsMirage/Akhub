## 结论

v1.1.31 已部署到生产，容器 `akhub` 运行 `ghcr.io/hsmirage/akhub:1.1.31`，
`healthy`、restarts=0、内外网 200。**配置身份与升级前逐项一致**
（13 分组 / 92 账号 / 128 Key / 236 逻辑模型 / 666 目标）。

没进 git）。生产在升级前跑的是手工打补丁的 `akhub:1.1.30-keepalive`——

## 二、升级动作

沿用前几版的 `release-1.1.31/` 目录约定（`stage.sh` + `rollback.sh` + `backup/`）：

1. `stage.sh` 备份 `docker-compose.yml`、把 `image:` 改成
   `ghcr.io/hsmirage/akhub:1.1.31`；
2. 用 `setsid nohup` 脱离会话执行 `docker compose up -d --no-deps akhub`
   （v1.1.28 那次 recreate 被 SSH 超时打断过，之后一律这样跑）；
3. compose 输出 `Recreate → Recreated → Starting → Started`，`EXIT=0`。

### 新字段在真实流量里落库（升级后约 20 分钟）

| 指标 | 值 |
| --- | --- |
| 请求 | 200 × 687、400 × 5 |
| 尝试明细 `ok` | 687 / 687 带 `upstream_status` |
| 尝试明细 `failed` | 27 条，18 条带 `upstream_status`（其余是网关自己判定的失败，按设计为 NULL） |
| `opaque_rejection` | 3 条，3 条都带 `upstream_status` |
| `effort_retry`（新增 outcome） | **4 条，4 条都带 `upstream_status` 与 `effort`** |
| `effort_retries > 0` 的请求 | 4 条 |
| 流式首字延迟已记录 | 671 条中 666 条有值（5 条是失败/中断，按设计留空） |

一条完整的「档位重发后换渠道成功」实录（`req_01M4ZEARPMM3JVY4J07TBPNYAC`，最终 200）：

| seq | outcome | upstream_status | 发出的档位 | 耗时 |
| --- | --- | --- | --- | --- |
| 1 | `effort_retry` | 400 | `max` | 2688ms |
| 2 | `opaque_rejection` | 400 | （不指定） | 7240ms |
| 3 | `ok` | 200 | `max` | 6052ms |

这正是本版要修的形状：**档位被拒 → 记下明细 → 换渠道 → 成功**，
而不是把上游的 400 原样丢给用户。升级前这种请求在库里只会是
`attempts=1`、两个状态码都是 NULL、日志里一个字都没有。

### 首字前心跳路径

升级后 20 分钟内 **66 条请求的首字超过 15 秒宽限期**（最长 181.1 秒）——
即心跳路径被真实触发，而这些请求全部拿到 200。这正是 524/522 的来源区间。

## 五、观察到的 ERROR 与判断

`docker logs` 里有 9 条 `ERROR akhub::multiplier::refresh: 超过半数账号倍率刷新失败，
判定为探针侧系统性故障，宽限期统一延长`。

**这不是本版引入的**：`git diff 100a9df..54fef34 -- src/multiplier/` 为空，
该模块本次一行未改；而且这正是 README「已知边界」里写明的设计行为
（探针失败不停用账号，保留最后已知值并进入宽限期）。属于 New API 探针侧
当前的凭证/网络状况，与本次发布无关。

## 六、回滚

```bash
bash /opt/akhub/release-1.1.31/rollback.sh
```

脚本先校验当前镜像确实是 `ghcr.io/hsmirage/akhub:1.1.31`，再恢复
`release-1.1.31/backup/docker-compose.yml`（指回 `akhub:1.1.30-keepalive`）
并 recreate。上一版镜像就在本机，回滚不需要重新拉取。

**本次是加列迁移，不应恢复数据库快照**：v22 只加列，旧二进制不读这三列，
向前兼容；恢复快照反而会丢掉发布之后的请求记录。

## 七、限制（如实记录）

1. **观察窗口短**（约 20 分钟、687 条请求）。心跳路径虽已被触发（66 条 >15s），
   但「档位阶梯走完换渠道」（`EffortExhausted`）在窗口内只命中 4 条
   `effort_retry`；P0-3 那条完整阶梯换渠道路径的正确性主要仍由编译机上的
   807 项测试（含 2 项专门覆盖它的 e2e）保证，不是线上观测。
2. **522 的建连根因不受本版影响**：本版修的是 524 与「首字前零字节」，
   522 是「EdgeOne 边缘 → 德国源站」的 TCP 建连超时，仍需按
   [2026-10-10 报告](2026-10-10_EdgeOne-522-复核与近端回源方案.md) 部署香港中转机
   （`47.76.54.171` 上 nginx 仍是 inactive）。
3. 上游 `supeai.top` / `newaicxy.xyz` 的首字延迟（p90 曾从 18s 恶化到 160s）
   是上游侧的问题，本版只保证这段等待不再被 CDN 判成源站无响应。
