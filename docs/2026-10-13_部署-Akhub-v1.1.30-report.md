# Akhub v1.1.30 部署记录（生产 89.58.17.138）

## 结论

v1.1.30 已部署到生产，容器 `akhub` 运行 `ghcr.io/hsmirage/akhub:1.1.30`，
`healthy`、restarts=0、内外网 200。**配置身份与升级前逐项一致**
（11 分组 / 88 账号 / 125 Key / 176 逻辑模型 / 570 目标）。

本版解决的是客户报的第二次 400：

    The request could not be processed. Please check the request parameters.

## 这次和上次不是同一个问题

| | 文案 | 能否归因 |
|---|---|---|
| v1.1.29 修的 | `requires adaptive thinking; omit thinking or use ...` | 能（形状/档位） |
| 本次（v1.1.30） | `The request could not be processed. Please check the request parameters.` | **不能** |

第二句指不出任何具体参数。定位过程：

* 同账号同 Key 的记录里 **1,609,463 B → 200，20 秒后 1,611,808 B → 400**；
* 直连上游复现 **200 多次**——按体积（49KB–2MB）、按形状（adaptive 各档位、
  老形状、采样参数、`cache_control`）、按并发（12 路突发）——**一次都没失败**。

结论：上游侧的间歇性故障，不是 Akhub 发错了什么。

## 改动

依据用户判断：**400 发生在开始生成之前，一个 token 都没消耗**，所以换渠道重试
几乎免费；直接透给客户端则把上游的抖动变成用户可见的失败。代价不对称，就该重试。

判据 `is_opaque_rejection` 两个方向都收紧：

* **必须**匹配已知的泛泛句式（`could not be processed` / `bad request`）；
* **只要**能归因到请求本身（`prompt is too long` / `invalid` / `must be` /
  `max_tokens` / `thinking` / `tool` / `image` / `message` …）就绝不重试——
  换到哪个目标都是同一个结果，重试只会白传一遍请求体（现场是 1.6 MB）。

处置：健康判定用 `Neutral`（分不清是客户端请求有问题还是上游抽了，**不能**把账
算到目标头上）；准入按 `Neutral` 结算、预扣额度退回，所以这次重试在 token 上
确实是零成本。有界：首次 + 最多 2 次换渠道，全都不行就把**上游原话**交回客户端。

## 复审时发现并修掉的缺陷

`last_opaque` 一旦写下就不再清除，于是这条路径会把错误的原因报给客户端：

1. 目标 A 返回无法归因的 400 → 记下 `last_opaque`，换渠道；
2. 目标 B/C 因为**别的原因**失败（限流、超时）→ 只更新 `last`；
3. 候选耗尽 → 把那个**早已过期**的 400 原样交回客户端。

结果：真正的原因是 429，客户端却收到 400——**错误码错了，客户端的重试行为也跟着
错**（429 该退避重试，400 不该重试）。

修法：凡是"最后一次失败"被改写的地方一并清掉 `last_opaque`——`run_attempt` 的
Switchable 分支、`note_unavailable`、`recheck_multiplier`。回归测试先撞一次无法
归因的 400、之后全部 429，断言客户端拿到 **429**；修之前该测试失败
（left: 400, right: 429），修之后通过。

### 归因判据在生产链路上的验证

这一步是本版最关键的验证——**判据太松会把真实的参数错误也重试一遍**。用真实链路
发一个可归因的 400：

```
POST /v1/messages  {"messages": []}
→ 400  field messages is required
```

结果：

* 日志是 `上游拒绝请求`，**不是** `换渠道重试`；`换渠道重试` 计数 = **0**；
* 尝试明细 `outcome=failed`（不是 `opaque_rejection`），说明它走的是普通参数
  错误分支，没有被判成"不可归因"。

判据按预期收紧了。

## 回滚

```bash
bash /opt/akhub/release-1.1.30/rollback.sh
```

脚本先校验当前镜像确实是 `1.1.30`，再恢复 `release-1.1.30/backup/docker-compose.yml`
（指向 1.1.29）并 recreate。旧镜像 `ghcr.io/hsmirage/akhub:1.1.29` 保留在本机。
本次没有数据库结构变更，**不应恢复数据库快照**覆盖发布后的请求记录。

## 观察窗口与限制

上线后观察：容器 `healthy`、restarts=0、无 panic、无 ERROR；功能验证 9/9 通过；
归因判据在真实链路上表现正确。

**限制（如实记录）**：`换渠道重试` 这条路径在观察窗口内**没有被真实流量触发**——
上游此刻没有在回那种不归因的 400（客户报的那次发生在 02:48，之后未再出现）。
该路径的正确性由编译机上的 793 项测试（含 4 项专门覆盖它的 e2e）保证，不是线上
观测。等上游再次抖动时，日志里会出现"上游 400 未消耗 token，换渠道重试"。

另外，本次观察窗口较短（约 10 分钟）且凌晨流量偏低，不足以覆盖完整分布。
