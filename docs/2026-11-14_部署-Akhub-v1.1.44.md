## 部署

```bash
cd /opt/akhub
sed -i 's|akhub:1.1.43|akhub:1.1.44|' docker-compose.yml   # 已留 .bak
setsid nohup docker compose up -d > /tmp/akhub-upgrade.log 2>&1 < /dev/null &
```

用 `setsid nohup` 是因为 stop_grace_period 是 200 秒：SSH 断线不能把重建留在半截。

### 重点核对：托管自动清理没有误删在售模型

本版唯一有数据面影响的行为是「托管下自动删除上游已消失的模型」。上线后立刻用
升级前的备份逐行对账：

| 指标 | 升级前 | 升级后 |
|---|---|---|
| 在售模型（`missing=0`） | 2544 | **2544**（一行没少） |
| 陈旧占位（`missing=1`） | 122 | 25 |
| 启用中的调度目标 | 1189 | **1189**（一个没少） |
| 逻辑模型 | 397 | 377 |

被清掉的 97 行**全部**满足 `missing=1`：升级前就已经标记为"上游已消失"、早就不
参与调度的占位行，正是这次要解决的那堆垃圾。仍在服务的模型与目标一个都没动。

> 剩下的 25 行 `missing=1` 是管理员改过下游模型名的行——按设计保留占位，不自动删。

## 已知观察（升级前就存在，非本次引入）

启动日志里有一批倍率探针与模型同步的告警，都是上游站点侧的问题，升级前就在发生：

- `/v1/sub2api/billing` 返回 404 / 401 / 403：几个 Sub2API 站点不再暴露该端点，
  账号退回最后已知倍率并进入宽限期（设计如此，不中断服务）。
- 6 个账号的「模型自动同步失败 · 上游模型列表请求失败」：上游 `/v1/models` 拉不到。
  **注意**：按本版新逻辑，拉取失败时什么都不改（不是清空），所以不会误删；只有
  成功拉到列表、且列表里确实没有的模型才会被删。
