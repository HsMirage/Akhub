## 本次改动

调度评分从四维扩到**五维，新增「缓存命中率」**，默认权重
40 / 25 / 15 / 10 / 10（首字与速度各让 5 分）。

命中率**不经参照系**：`得分 = 缓存读 Token ÷ 全部输入 Token`，天然 0-1，
与可靠性同类。两个边界各有用例钉住：

- **「没上报」≠「没命中」**：上游不报缓存字段时取中性 0.6，不是 0。
  用 `cache_samples` 单独计数——命中率 0 本身是正常取值（冷前缀）。
- **v24 迁移把旧预设升级为五维**：见下。

顺带修好一处**既有的口径分叉**：`usage_breakdown` 的 `input` 在三个协议间
不一致。非流式 Anthropic 的命中率分母偏小，真实命中 30% 会算出 300% 并被
clamp 成 1.0。判据不能用字段名——**Responses 和 Anthropic 都用 `input_tokens`，
语义相反**，要看"缓存读写是否在顶层 `cache_*_input_tokens`"。

## 数据库迁移（v23 → v24）

先在**生产库快照**上预演，再上生产：

| 检查 | 结果 |
|---|---|
| schema_version | 23 → **24** |
| `groups.weight_cache_hit` | 已加，**14 个分组全部正确映射** |
| `target_perf_snapshot.cache_hit` / `cache_samples` | 已加 |
| 权重和 | 全部仍为 100 |
| 残留 0 权重的分组 | **0 个** |
| `PRAGMA integrity_check` | **ok** |
| 各表行数 | 只增不减（详见下表） |

**迁移不只是加列。** 原设计给 `weight_cache_hit` 默认 0，代价是新维度
**上线当天就是死的**——现场 14 个分组全是从预设点出来的，升级后命中率
权重一律 0。发版前在生产快照上发现这一点，改成只做一件可证明无歧义的事：
四个数与旧预设**完全相等**的分组，换成同名新预设。

```
成本优先 55/20/15/10 → 55/20/10/5/10     （8 个分组）
均衡     40/25/20/15 → 40/25/15/10/10    （6 个分组）
质量优先 15/30/25/30 → 15/30/20/25/10    （0 个，现场没用过）
```

相等才动，说明当初是点的按钮而非手调；手调组合几乎不可能恰好等于预设。
有一条用例专门钉这个边界（33/27/21/19 保持原样、第五维留 0）。

生产启动日志实拍：


## 备份与回滚

备份目录：`/opt/akhub/release-1.1.36/backup/`

- `akhub.sqlite` — 发布前一致性快照（`python3 sqlite3 backup`），594 MB，
  `integrity_check` = ok，各表计数核对一致
- `master.key` — 主密钥副本（600）
- `docker-compose.yml.before-1.1.36` — 发布前的 compose（image 指向 1.1.35）
- `previous-image.txt` — 旧镜像 id `sha256:2791dc81…`

回滚（只换镜像、**不动数据目录**）：

```bash
cd /opt/akhub
cp -p release-1.1.36/backup/docker-compose.yml.before-1.1.36 docker-compose.yml
docker compose up -d --no-deps akhub
curl -s http://127.0.0.1:8088/health/version
```

v1.1.36 **没有破坏性结构变更**（只加列），旧版二进制用 `SELECT *` 读新库正常
（忽略多出来的列），回滚后能直接跑同一个库。

**但有两处语义变化要注意**：

1. 回滚到 1.1.35 后，14 个分组的权重已经是五维映射后的值（和仍为 100）。
   旧版只读前四项，实际变成 55/20/10/5 与 40/25/15/10——比原来的
   55/20/15/10 和 40/25/20/15 略偏向首字。想要完全复原，回滚后把权重
   手动改回旧值，或从 `release-1.1.36/backup/akhub.sqlite` 里抄。
2. 升级后 Anthropic 上游的 `request_records.input_tokens` 比旧记录大一截
   （含缓存）。跨版本对比用量/成本趋势时不能直接相比。

**不要**用备份快照覆盖生产库，那会丢掉切换后产生的请求记录。
