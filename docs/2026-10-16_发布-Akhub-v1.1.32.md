# 1.1.32 发布记录

发布时间：2026-10-16
主机：Vienna（89.58.17.138）
镜像：`ghcr.io/hsmirage/akhub:1.1.32`

## 这次修了什么

### 1. 配置乐观锁误报（用户主诉）

"明明没人操作过、刚刷新页面、刚填完点保存就报配置已被其他会话修改"。

根因是版本号语义错了：旧实现每次 `reload_config()` 都无条件 +1。而这条路的
调用点远不止管理员改配置——后台托管模型同步（`tasks::model_sync`，默认 30 分钟
一轮）每轮都会 reconcile 一次，于是管理员刚填完表单，一次与他无关的后台同步就把
版本顶掉了，点保存必 409。

现在只有**配置内容真的变了**才推进版本（`RuntimeConfig::same_config`，用派生
`PartialEq` 整体比较而非手写字段清单）。

配套前端改动：冲突提示不再整页重载（那会丢掉正在填的表单），改为原地取回最新
配置；与配置无关的写操作（测试连接、倍率预览）不再带乐观锁头。

另修：空库首启版本是 0，而客户端把 0 当作"还没读到过"，等于锁静默关闭——
现在从 1 起步。

### 2. 容器部署的一键升级

镜像里的 `/usr/local/bin/akhub` 在只读层、属主 root，以非 root 运行的服务进程
覆盖不了它——这是容器部署一直升不了级的原因。同机部署的 sub2api 能一键升级，
是因为它的二进制 `/app/sub2api` 在容器**可写层**、属主就是运行用户：它覆盖自己
后退出，靠 `restart: unless-stopped` 把同一个容器拉起来。

这里照搬同一思路但不要求镜像层可写：入口脚本把二进制复制到数据卷的 `runtime/`
下再运行那一份。数据卷持久、属主即运行用户，于是进程能替换自己、退出后由
restart 策略拉起，升级得以保留；运维 `pull + up -d` 换镜像时入口脚本会发现镜像
版本变了并刷新卷里那份，所以**回滚照常有效**。容器与原生二进制因此共用同一段
升级实现，不再需要宿主机上跑任何代理，也不需要挂 docker socket。

## 复审另外修掉的四个真问题

1. **升级成功后进程死锁、永不退出**——`started_at` 的 `lock()` 写在 `set_progress`
   的**实参**里，临时 `MutexGuard` 活到整条语句结束，而 `set_progress` 内部又要锁
   同一个不可重入的 `Mutex`。现场表现极具迷惑性：二进制已替换成功、日志停在
   "准备重启"，进程既不退出也不重启，管理接口再无响应——线上等于完全没生效。
2. **前端在旧进程还应答时就刷新**——优雅关闭期间 `/health/version` 仍由旧进程
   应答且报旧版本号，按"能应答就刷新"会让用户看到旧版本。现在等到版本号真的
   变成目标版本才刷新。
3. **面板永久卡住**——前端只认服务端的 `done`，而容器路径下 `done` 往往来不及被
   看到（旧进程写完就退出）。现在用"见过 running 之后又变 idle"识别进程被替换，
   并给连续失败兜底。
4. **重开面板不再跟踪进度**——轮询只看组件本地的 `upgrading`。

## 备份与回滚

备份目录：`/opt/akhub/release-1.1.32/backup/`

- `akhub.sqlite` — 发布前的一致性快照（`VACUUM INTO` 取的，对运行中的库也一致，
  不会漏掉 WAL 里已提交的事务），sha256 记录在案
- `master.key` — 主密钥副本（600）
- `docker-compose.yml.before-1.1.32` — 发布前的 compose
- `previous-image.txt` — 旧镜像 id `6aa0a8d272cc`（`ghcr.io/hsmirage/akhub:1.1.31`）

回滚（只换镜像、**不动数据目录**）：

```bash
cd /opt/akhub
cp -p release-1.1.32/backup/docker-compose.yml.before-1.1.32 docker-compose.yml
docker compose up -d --no-deps akhub
curl -s http://127.0.0.1:8088/health/version
```

**不要**用备份快照覆盖生产库：1.1.32 没有数据库结构变更，回滚后旧版本能直接读
同一个库；用快照覆盖反而会丢掉切换后产生的请求记录。

## 发布过程中发现并修掉的一个回归（重要）

第一次 CI 的 `docker` job 抓到一个**本次改动引入的真回归**：入口脚本把
"准备可自更新的二进制副本"这类信息打到 **stdout**，而

```
docker run <镜像> --version
```

是用户脚本与 CI 都会写的用法，它的输出**必须是纯版本号**（CI 的断言是
`[[ "$got" == akhub\ * ]]`）。多打一行之后真正的版本号被挤到第二行，解析全坏。

改成信息性输出一律走 stderr（`docker logs` 两者都收，诊断信息照样看得到）。
已在服务器上用官方镜像实测：stdout 就是 `akhub 1.1.32`，stderr 是那行提示。

## 发布过程记录

1. 服务器本地构建镜像（GHCR 推送权限在本机 token 上缺失），先做隔离冒烟：
   用**生产数据的副本**起容器，22 张表计数一致、`integrity_check` = ok；
2. 备份生产数据（`VACUUM INTO` 一致性快照 + master.key + compose + 旧镜像 id）；
3. 只重建容器、不动数据目录，逐表比对一致；
4. 切到 CI 产出的官方镜像，确认"运行中 == 已发布"（镜像 id 相同）；
5. CI 红了一次（stderr 回归），修好、重编、重推，并把 tag 移到修复后的提交，
   让**已发布产物与源码一致**。

最终状态：`ghcr.io/hsmirage/akhub:1.1.32`（`323156770c1f`），生产运行的就是它，
CI 的 `check` 与 `docker` 两个 job 全绿。
