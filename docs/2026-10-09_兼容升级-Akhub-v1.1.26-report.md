# Akhub v1.1.26：新代 Claude 的思考契约、连接池加固与错误脱敏入库

## 结论

1.1.26 已部署到生产 Akhub（89.58.17.138，容器 `akhub:1.1.26`），内外网验证通过、容器
`healthy`、重启次数 0，切换前后配置哈希完全一致（10 个分组 / 82 个上游账号 / 103 把 Key /
165 个逻辑模型 / 534 个调度目标）。

本次有三件事：

1. **主线修复**：思考参数改为按**真正要发出去的上游模型**的契约发射，解决
   `claude-opus-5-5 requires adaptive thinking; omit thinking or use thinking.type=adaptive
   and output_config.effort` 这类 400。
2. **线上事故处置**：生产库的连接池被一条卡住的连接占死约 31 小时（请求记录被丢弃、
   `/health/ready` 503、容器 `unhealthy`）。本次把池从 1 条放宽到 4 条并加 5 秒
   `acquire_timeout`，重启后 `/health/ready` 恢复 200（约 1 毫秒）。
3. **入库**：此前已在生产运行、但一直没提交的 1.1.24 / 1.1.25 改动（上游错误脱敏、
   异步生图兼容、长思考不再撞总时长上限）随本次一并入库。

## 修改内容

### 1. 思考参数按上游模型契约发射（主线）

- `src/protocol/canonical.rs`：`Effort` 增加 `XHigh` / `Max`（自适应契约专有），
  新增 `as_openai_level()` 把这两档折成 `high` 再发给 OpenAI 两个协议；新增
  `ThinkingDisplay`（`summarized` / `omitted`）与 `ThinkingConfig.display`、
  `explicit_effort()`（区分"客户端没表态"与"客户端要了 medium"）。
- `src/protocol/anthropic.rs`：新增 `ThinkingContract`（`adaptive` / `display` /
  `no_sampling` 三个事实）与 `align_thinking()`。分类**只对已知老家族回落**到手工契约
  （claude-3、4.0/4.1/4.5 系），其余带版本号的 Claude（含 `claude-opus-5-5`、`claude-fable-5`
  与还没见过的下一代）一律按现代契约走；Kimi/Moonshot 的 Anthropic 兼容端点按自适应处理；
  非 Claude 端点与没有版本数字的名字仍走手工契约。
- 发射规则：自适应模型发 `thinking: {"type": "adaptive"}` + `output_config: {"effort": ...}`，
  不再发 `budget_tokens`；客户端显式关闭时**省略** `thinking`（`{"type":"disabled"}` 会被 400）
  并记一次 `thinking` 降级；跨协议时补 `display: "summarized"`（4.7 起默认 `omitted`，
  不显式要就拿不到思考文本）；4.7+ 模型上 `temperature`/`top_p`/`top_k` 按白名单丢弃并标记。
- 解析侧接受 `thinking.type = "adaptive"`、`thinking.display` 与顶层 `output_config.effort`；
  `output_config` 进入已知字段，其它子字段（如 `format`）仍按"不能表达就报错"处理。
- `src/gateway/passthrough.rs`：跨协议发射后按**上游模型名**再对齐一次，逻辑模型名只是别名
  （`claude-opus-5-5[1M]`、分组名）时也不会把形状发错；`Translation::thinking()` 提供原始意图，
  避免把客户端没要过的档位猜成 medium。

### 2. 连接池加固

`src/storage/mod.rs`：`max_connections(1)` → `4`，并加 `acquire_timeout(5s)`。单连接是
单点：一条连接被卡住之后，请求记录、Responses 状态、粘性落盘与 `/health/ready` 会一起挂住。
写仍然由 SQLite 串行化，冲突由既有的 `busy_timeout(5s)` 兜底；迁移里 `PRAGMA foreign_keys`
本来就是"独占一条连接"的写法，不受影响。`tests/release_harden.rs` 里那处 `PRAGMA foreign_keys = OFF`
改为与后续写入共用同一条连接（PRAGMA 是连接级的，池里不止一条连接时原写法会失效）。

### 3. 随本次入库的历史改动

上游错误脱敏（`ErrorRedactor` / `PublicMessage`：保留可操作的原因、抹掉账号名、Base URL、
Key 与任何 URL）、异步生图任务兼容、长思考不再被总时长上限掐断、Responses 开场用量不冒充
最终用量、前端请求页与设置页调整。

## 线上事故与根因

- 时间线：容器 2026-10-06 17:01 UTC 启动，2026-10-08 12:31:42 UTC 起出现第一条
  `pool timed out while waiting for an open connection`，此后 10210 条同类日志，直到本次重启。
- 症状：请求记录批量丢弃（`写入请求元数据失败，本批已丢弃`）、Responses 状态保存失败、
  粘性绑定与性能快照落盘失败、倍率刷新跳过、`/health/ready` 30 秒后 503、容器 `unhealthy`
  （FailingStreak 2459）。网关转发本身不受影响，所以外部只表现为"统计与续链悄悄坏掉"。
- 已排除：SQLite 层面没有锁——事故期间用另一条连接执行 `BEGIN IMMEDIATE` 立即成功；
  数据库 `quick_check` 为 ok；进程 7 个线程无 D 状态、无磁盘 I/O 阻塞；磁盘 28% 使用。
  因此是**池层面的连接被某个任务长期占住**（或信号量泄漏），不是数据库损坏或 I/O 故障。
- 处置：重启（随本次发布）+ 池放宽到 4 条 + 5 秒快速失败。
- 剩余风险：**具体是哪条调用路径占住了连接仍未定位**。建议后续加一个"池耗尽看门狗"
  （连续 N 秒 `num_idle() == 0` 时打点告警），把下一次复现变成可定位的证据。
