# 工具请求误拦修复

## 结论与影响

已删除按历史参数错误屏蔽后续请求的机制，以及「调度屏蔽」页面和接口。服务器已部署修复版 `1.1.21`，用户无需再手动放行。

影响所有账号：参数错误只影响本次调用，后续请求继续由上游实际处理。鉴权、额度、限流、熔断、端点选择和协议转换规则仍按各自职责工作。没有新增依赖或数据库迁移。

## 现场证据

范围：`AwsClaude` 分组的「华强北高智商 kiro」账号，模型 `claude-opus-5-5`。

在同一台服务器上，使用账号现有上游凭据与对应分组凭据，比较同一份请求正文、同一 Messages 端点。凭据仅在内存中使用，未写入本报告或测试输出。

| 请求 | 直接调用上游 | 修复前经过 Akhub | 修复后经过 Akhub |
| --- | --- | --- | --- |
| 普通工具选择 `auto` | 200，返回 `tool_use` | 本次对照为 200 | 200，返回 `tool_use` |
| 强制选择 `any` | 400，明确说明不支持强制工具选择 | 重复报错后为本地 503 | 连续四次均为原始 400 |
| 指定工具 `tool` | 400，同一参数错误 | 本地 503 | 同一原始 400 |
| 上述错误后的 `auto` 流式请求 | 200，正常结束 | 旧机制可能依据历史错误拦截 | 200，收到完整 `message_stop` |

修复后共完成 7 组直连／转发对照，全部通过。普通工具请求验证了真实工具调用，流式请求验证了结束事件，并非只检查 HTTP 状态。

第一次直连探测使用 Python 默认客户端标识时遭到站点 403；对齐 Akhub 的客户端标识后完成上述对照。该首次 403 不作为参数能力或网关故障的证据。

## 原因与修复路径

1. 较早版本将「不支持强制工具选择」理解成「不支持工具调用」，从而牵连普通工具请求。
2. `1.1.19` 缩小了归因范围，但仍会在两次拒绝后创建跨请求限制。`1.1.20` 的现场对照显示：直接请求得到上游 400，经网关却在发往上游之前返回 503。
3. 新增的页面只能查看、清除限制，不能证明下一次请求仍应被拒绝。请求参数、凭据、端点和上游实现都可能改变结果。
4. `1.1.21` 删除错误文本归因器、限制缓存、调度资格检查，以及配套页面与接口。错误仍按原有同协议透传／跨协议转换规则返回；没有擅自删除工具或把强制选择改成 `auto`。

## 验证与回退

- 新增三条回归测试：连续错误保持原始状态码、上游恢复后相同请求立即成功、不同请求形状及流式调用不被连坐。三条在旧代码上均失败，修复后均通过。
- 完整后端测试集通过 707 项。随后清除仅服务于已删除接口的端点解析器及其一项测试，最终复验 436 项单元测试和 3 项现场回归测试全部通过。
- `cargo clippy --locked --all-targets -- -D warnings`、格式检查、前端测试与构建通过。
- Linux 在指定共享编译机编译；服务器独立测试容器通过就绪、版本、管理页及实际前端资源检查后，才切换线上服务。
- 切换前后均为 10 个分组、73 个账号、96 把 Key、162 个逻辑模型、503 个调度目标。
- 原部署配置、数据库一致性快照和主密钥保存在服务器 `/opt/akhub/hotfix-1.1.21/backup`。数据结构未变，回退只需恢复原部署配置并重建 Akhub 容器；无需恢复数据库或丢弃新的调用记录。
- 服务使用本次构建的本地镜像 `akhub:1.1.21`；公开发布尚未执行。

复现回归测试时，在项目根目录执行：

```bash
cargo test --locked --test capability_forwarding
```

## 边界

上游确实拒绝 `any` 和指定工具参数；修复网关不会使上游获得它不支持的能力。这些请求现在返回真实的参数错误。可正常使用的是自动工具选择及其流式调用。

历史请求记录不保存完整请求正文，因此没有声称逐字还原用户最初报错时的调用。结论来自原改动记录、服务器请求元数据以及上述实际对照。
